# Conformance coverage and report migration

Status: binding design for the next implementation; no new writer, reader release, downstream migration, or compatibility execution is established by this document.

Decision date: 2026-09-05. Owner: ESS. Planning authority: story:review-conformance-format-design; implementation is split between story:a-skipped-scenario-is-not-a-failed-one and story:review-conformance-coverage. This decision answers review F03.

## Decision

Freeze the bytes and meanings of standalone report **ess-conformance-report/1** and suite **ess-conformance/1–4**. Introduce **ess-conformance-report/2** for explicit, producer-specific outcome partitions and exact-suite binding, and **ess-conformance/5** for durable coverage and selection. Report/1 remains restricted to suite majors 1–4 even when execution readers add suite/5; suite/5 requires report/2. New reports can describe admitted legacy suites, but their coverage remains unknown and cannot qualify as complete. A report's execution verdict remains the producer's verdict; coverage qualification is a separate, explicit result.

Move readers and consumers before writers. Do not enable a new default until the Atlas migration ADR, every relying reader, generated-runtime regeneration, cross-language fixtures, and the shipped-version record are complete. Increasing a version string does not make today's suite readers refuse it.

This is an ESS contract. AEP transcribes and adapts it at its own boundary; ESS gains no AEP dependency. The specification skill's Rust-owned type and explicit-coverage rules apply. This document defines persisted contract types; it does not introduce an authored ESS business domain or implement those types.

## Frozen execution semantics

For the following table, one terminal scenario contributes one to total. A v1 list entry is exactly the status word, one ASCII space, then the opaque scenario identity. It is not parsed by splitting the identity into words. scenarios_failed is the length of the entire non-pass list, regardless of its misleading name. Rust and Go both preserve this meaning. No skipped/error/unsupported category is retroactively relabeled failed. [S1, S2, S5]

| Producer scenario result | v1 count/list contribution | v2 category contribution | Producer aggregate contribution |
| --- | --- | --- | --- |
| Rust passed | total +1; no failure entry | passed +1 | No adverse contribution |
| Rust failed | non-pass +1; "failed ID" | failed +1 | failed |
| Rust error | non-pass +1; "error ID" | error +1 | inconclusive unless any scenario is failed or unsupported |
| Rust unsupported | non-pass +1; "unsupported ID" | unsupported +1 | failed, including beside a separate error scenario |
| Go passed | total +1; no failure entry | passed +1 | No adverse contribution |
| Go failed | non-pass +1; "failed ID" | failed +1 | failed |
| Go skipped | non-pass +1; "skipped ID" | skipped +1 | inconclusive unless some scenario failed |
| Go ordinary command/begin/end error | failed as the final result, not a new error category | failed +1 | failed |
| Go ErrUnsupported/unsupported step or expectation | skipped, unless teardown overrides it | skipped +1 | inconclusive absent a failure |
| Go skipped followed by EndScenario error | final result failed; no additional skipped entry | failed +1 | failed |

Rust check aggregation within one scenario remains **failed > error > unsupported > passed**. Therefore an error and unsupported check in the *same* scenario yield error, while separate error and unsupported scenarios yield a failed run. Go teardown failure remains a failure even when its error happens to be ErrUnsupported. The v2 producer profiles below record these existing distinctions rather than promise identical semantics. Unsupported vocabulary in an admitted new-format suite is a document/reader refusal *before* execution; the legacy fallback behavior in the table remains relevant to old runtimes only.

For either producer, zero terminal scenarios currently aggregates to passed. Freeze that execution fact in v1; do not infer complete conformance from it. Rust detailed status error maps to standalone inconclusive. Rust CLI currently exits 0/1/3 for passed/failed/error. Go's test process may exit zero when all selected subtests skip while its standalone report says inconclusive; Go test success is not conformance qualification. [S2, S5, S6]

The current validated v1 reader accepts both non-pass vocabularies because v1 carries no producer profile. It does not establish exact-suite binding, complete coverage, or uniqueness of opaque listed scenario IDs. Do not strengthen those unknown historical claims by upgrading a report. Keep the existing v1 shape and admitted meanings separate from v2's stronger invariants. Its suite_version admits exactly ess-conformance/1, /2, /3 and /4 forever under report/1. The future v1 reader must use that frozen allowlist, not the general SuiteFormat::is_supported helper after it grows to include /5. A v1 document naming suite/5 is refused by Rust and every migrated reader; no v1 writer may create it. [S1]

Legacy timestamps do not have one shared signed domain: Rust's standalone completed_at and detailed started_at/completed_at use Timestamp(u64), while Go's standalone completed_at uses int64 from time.Now().UnixMilli(). Freeze those v1 writers and readers, including Rust's refusal of negative timestamp input and preservation of values above i64::MAX. Do not widen a legacy reader, narrow a valid Rust timestamp or reinterpret negative Go output to create retrospective cross-producer agreement. [S1, S2, S5, S11]

## New suite: ess-conformance/5

The closed top-level object has exactly **provenance**, **scenarios**, and **coverage**. provenance has the existing fields in S3, with suite_version fixed to ess-conformance/5. scenarios retains the v4 scenario/step/dependency vocabulary and its ID-keyed map. Version 5 adds no execution step semantics. Unknown fields are refused throughout typed envelopes and tagged variants; arbitrary keys inside an existing declared payload Node remain payload data, not unknown envelope fields.

coverage has exactly the following fields. Every field is emitted, including empty lists; nullable values are JSON null. Existing nested v4 scenario fields retain their declared optional/default rules.

| Field | Closed type and meaning |
| --- | --- |
| selection | Selection object defined below; the boundary against which completeness is assessed |
| knowledge | complete_inventory or unknown; complete_inventory means the builder enumerated the selected obligation/source inventory, not that execution passed |
| generated | Sorted distinct selected generated ScenarioIds |
| authored | Sorted distinct selected authored ScenarioIds |
| outside | Sorted list of Outside records |
| refused | Sorted list of Refusal occurrences, preserving multiplicity even when records are identical |
| authored_sources | Map from repository/input-root-relative source identity to {digest, scenario, disposition}; digest hashes the exact file bytes as sha256: plus 64 lowercase hex digits, scenario is its known ScenarioId or null, and disposition is accepted or refused |
| counts | Object with generated, authored, outside, refused; unsigned counts equal the corresponding list lengths |

Selection is exactly:

- scope: tagged object {kind: system}, or {kind: component, component: ComponentName}. A component name must resolve against the model when building the suite and agree with provenance.component.
- origins: one of generated, authored, generated_and_authored.
- filter: {kind: all}, or {kind: explicit, ids: [ScenarioId], parent: SuiteReference}. Explicit IDs are sorted/distinct; parent is the exact admitted parent suite, not merely its model digest.

For generated or combined selections, the inventory includes every generated obligation within the stated component/system boundary. For authored or combined selections, authored_sources includes every requested source file, including files whose compilation was refused. Selecting zero authored files is explicit; it does not claim the repository has no authored requirements. The builder must record the actual resolved source set instead of relying on a later process's working directory. Each accepted authored source has a nonnull ID identifying exactly one selected or outside authored scenario; exactly one accepted source owns each such ID. Refused sources retain the ID when known, even when another source with that ID was accepted, and have at least one refusal naming that source. Disposition is the final inventory result after merging, not merely compile_one success: a successfully compiled candidate rejected by a later merge is refused. Duplicate source identities with conflicting bytes refuse admission. No accepted source, refused source or known ID is erased to make the lists disjoint.

An Outside record is exactly {scenario, origin, reason, needs}: scenario is a ScenarioId; origin is generated or authored; reason is other_component, origin_selection or selection_filter; needs is a sorted/distinct list of existing EssSemanticRefs, nonempty for other_component and empty otherwise. origin_selection records a known candidate whose origin is excluded by a newly built origin selection. It represents a known executable candidate intentionally outside the selection, not an adapter failure. It can have a refusal beside it; the two records answer different questions.

A Refusal record is exactly **{origin, scenario, subject, source, code, message, effect, retained, scope, needs}**:

| Field | Closed type and meaning |
| --- | --- |
| origin, scenario, subject, source | Generated or authored origin; known ScenarioId or null; existing EssSemanticRef or null; authored-source identity or null. Preserve every known identity. Generated refusals require subject and null source; authored refusals require the rejected source identity and may have null subject. |
| code, message | Existing producer diagnostic code spelling and nonempty diagnostic text, including the original cause text; code is from the closed baseline RefusalCause/Cause vocabulary. |
| effect | check_not_emitted or candidate_not_emitted. This describes what was omitted, independently of whether a runnable scenario with the same ID survived. |
| retained | null if no selected/outside scenario has that ID; otherwise exactly {origin, source}, naming the surviving scenario's origin and accepted authored source identity, or null source for a generated survivor. It references the same scenario ID; it does not invent an execution result for the rejected candidate or claim that the survivor checks the omitted obligation. |
| scope | in_scope, outside_component or outside_origin, under the rules below; this is coverage applicability, not execution status. |
| needs | Sorted/distinct existing EssSemanticRefs establishing other-component requirements when scope is outside_component; empty otherwise. |

The baseline cause-to-effect mapping is exhaustive, not a code-name heuristic. **ViewUndecidable, OrderUnwitnessed, InvariantUnobservable and RefusalUndeclared** map to check_not_emitted. **NoWitness, GuardUnevaluable, GuardUnsatisfiable, InstanceRequired, NotSynthesisedYet, BindingUnobservable, ValueInvariantUnwitnessed, DuplicateScenario, StrategyWithoutGuard and WitnessRejected** map to candidate_not_emitted. Every authored Cause variant maps to candidate_not_emitted, because authored compilation does not admit a partial file. InvariantUnobservable may have retained null when every invariant was unobservable: holds_after then emits no scenario, while still preserving each missing-check refusal. The effect must not be inferred solely from final ID membership. [S7; synthesize.rs:502–526, 2910–2976; authored.rs:1049–1090, 1416–1483]

DuplicateScenario keeps the first generated scenario. Authored Duplicate keeps the first accepted file in deterministic source order; the refusal's source is the later rejected file and retained.source is the existing Cause::Duplicate.first identity. Both source digests stay in authored_sources. The same representation covers a non-duplicate authored compile failure followed by a successful different file with the same ID: the rejected file contributes a candidate_not_emitted refusal and the successful file is retained. Never synthesize an absent-scenario claim merely because compilation refused one candidate. Generated/authored merge collisions likewise retain the established scenario and attach a rejected-candidate diagnostic with both known origins. Future mapping must preserve every producer occurrence, the baseline code and its cause text, exhaustively cover the producing matches, and fail when a variant lacks a mapping; it cannot erase the ID, omit a refusal, discard the useful scenario or relabel a code to fit the schema.

Scope is assigned against the declared scope/origins **before explicit filtering**:

1. A refusal whose origin is excluded is outside_origin. It remains in a retained parent inventory; it cannot qualify a broader origin selection.
2. Within a component selection, a refusal is outside_component only when the builder establishes that its whole refused candidate/obligation requires another component and records the nonempty needs. A retained scenario's matching other_component entry can establish this for an omitted check known to belong to that surviving candidate. A rejected or absent candidate requires its own resolved dependency information: an outside survivor with the same ID does not prove that a duplicate candidate requires the same component. A subject name alone, an unknown authored source or missing dependency information cannot establish exclusion: use in_scope conservatively. Every known outside-component refusal remains visible.
3. All other refusals are in_scope, including omitted checks beside selected scenarios, rejected duplicate candidates for selected IDs, and unlocatable source/construct refusals. A system selection never uses outside_component.
4. An explicit filter may only narrow its admitted parent's IDs, not change its scope or origins. It copies all parent refusal occurrences with their full multiplicity, effects, retained identities, scope and needs unchanged; copies the full authored_sources map; retains previous outside entries; and adds omitted selected IDs as selection_filter. Thus a scenario moved outside by a filter can still have an in_scope refusal beside it. Filtering its ID out cannot turn the parent's incomplete claim into a complete one. Component/origin changes require a newly built selection with justified scope assignments, not a filter rewrite.

The following invariants are binding:

1. generated and authored are disjoint and their union is exactly the scenario-map keys. Every selected scenario has one origin; adding an authored candidate under an already retained ID is a refusal, not replacement.
2. IDs in outside are unique and absent from selected IDs. **Refusal scenario IDs need not be disjoint from either set.** For every nonnull refusal ID, retained is nonnull exactly when the ID is selected or outside, and identifies that surviving scenario and its accepted source. Otherwise retained is null. Null scenario requires null retained. A check_not_emitted with no survivor is valid, including the all-invariants-unobservable case.
3. refused is a **sorted list with multiplicity, not a set**: emit one array element per actual producer occurrence, including identical records concerning the same ID or source. Do not deduplicate, add an occurrence identity, or fabricate ordinal message suffixes. Sort outside by scenario then origin/reason; sort refused by origin, source, subject, scenario, code, effect, retained.origin, retained.source, scope, needs, message, with null before text and needs compared lexicographically. Equal complete sort keys give identical record bytes, so their relative order cannot change canonical bytes. Preserve full multiplicity whenever an inventory is retained through component/origin selection, explicit filtering, report coverage or parent equality checks. Selected/outside scenario IDs, authored-source map keys and report outcome IDs retain their existing uniqueness rules.
4. counts.generated + counts.authored equals the selected scenario-map size. A retained selected scenario contributes exactly one terminal execution result regardless of how many refusals name it; a retained outside scenario contributes none. Rejected candidates and missing checks contribute no execution result or outcome category. counts.refused equals the array's occurrence count, including identical records and outside_component/outside_origin occurrences; it is never an additional scenario or failure count.
5. Complete coverage requires complete_inventory and no refusal occurrence with scope in_scope; the predicate depends on existence, not the number of distinct records. An all-pass selected scenario with an in_scope omitted check or rejected candidate leaves conformance_status inconclusive. Outside scenarios and correctly justified outside-component/origin refusals do not make a complete named selection incomplete; they still prevent its result from satisfying a broader expectation.
6. Generated-only, authored-only, component, and filtered selections never become whole-system combined coverage merely because their own inventory is complete.
7. An imported legacy suite cannot acquire complete_inventory from its nonzero scenario count or its provenance. Keep its legacy suite version and use unknown coverage in a diagnostic v2 report; do not manufacture v5 generated/authored origins by conversion. Rebuilding from the source/model inventory creates a new v5 suite and digest. An external v5 producer that knows scenario origins but cannot establish the full inventory must use unknown.
8. Unknown component, duplicate scenario IDs or JSON object keys, inconsistent inventory/counts/source ownership/retained identity/scope, unrecognized vocabulary, and an explicit filter whose parent/IDs or retained inventory cannot be validated refuse suite admission. Legitimate scenario/refusal coexistence is admitted for diagnostic execution, not refused as malformed. Coverage claims are builder claims; bytes alone cannot prove that a builder enumerated all semantic obligations, preserved every original producer occurrence or justified component exclusion. Qualification additionally requires the caller's approved exact suite/selection.

Repeated source constructs are a concrete multiplicity case: entity conversion retains invariant entries and holds_after pushes one refusal per unobservable invariant; authored Compiler::run visits each assertion and Compiler::refuse appends each refusal. Two identical unobservable invariants or undeclared-view assertions therefore remain two refusal elements with the same record bytes. The known scenario/source identity remains intact and neither occurrence adds an execution result. [ess-domain/src/entity.rs:1566; synthesize.rs:2945–2959; authored.rs:1543–1548, 1600–1602, 1893–1898]

These obligations are owned by story:review-conformance-coverage. Fresh synthesis, authored-only compilation, component filtering, CLI --path merging, Go emission and web emission must each preserve the same inventory. Legacy diagnostic execution retains the legacy suite and makes no inventory claim.

## Exact-suite digest and serialization

A SuiteReference is the closed object **{version, digest_profile, digest}**. version is the admitted suite format. digest_profile is exactly **sha256-json-bytes/1**. digest is sha256: followed by 64 lowercase hexadecimal digits.

The digest is SHA-256 over **every byte of the actual UTF-8 JSON suite document issued to the runner**, including the final newline when present. It excludes file names, build stamps, transport headers and enclosing report bytes. It is not spec_digest, contract_digest, a scenario-ID hash, a reduced Go struct hash, or a hash of YAML output. The suite does not contain its own digest; the runner/report, optional parent reference, and expected-suite policy carry it.

This decision intentionally binds an exact serialized artifact. Reformatting equivalent JSON, changing field order, replacing 1 with 1.0, changing Unicode escape spelling, omitting an explicitly written default, or changing LF to CRLF yields a **different digest**. Readers never parse and reserialize before hashing. An expected-digest mismatch refuses execution/adaptation; a missing suite can be archived as an unverified report but cannot qualify as exact-suite evidence.

Canonical generation is a writer requirement, distinct from byte identity:

| Concern | Frozen legacy writers | v5 writer rule |
| --- | --- | --- |
| Object fields | Existing typed field order and BTreeMap order; no rewrite | All object keys, including typed objects and payload maps, sorted by UTF-8 byte order |
| Layout | Existing serde_json pretty form plus trailing LF | Two-space indentation, colon followed by one space, LF line endings, nonempty arrays/objects on multiple lines, empty arrays/objects as []/{}, exactly one trailing LF, no BOM |
| Omission | Existing optional/default omissions, including absent provenance.component | Existing nested scenario/provenance omission rules remain; every newly defined coverage field is present and nullable fields use null |
| Counts and integer fields | Existing valid spellings and producer-specific timestamp domains preserved | Unsigned decimal integers without exponent, sign or leading zero; bounded to u64 and checked before arithmetic. The new report/run timestamps use this same exact integer rule; payload numbers below remain a separate domain |
| Payload numbers | Existing admitted finite Number semantics preserved | Finite binary64 values only for existing Node numbers; retain the numeric rendering behavior of serde_json 1.0.151 and its locked formatter at this baseline, including signed zero and integral-float spelling; do not coerce to integer or string |
| Strings | Existing bytes preserved | UTF-8, no Unicode normalization; quote/backslash/control escapes as the baseline serde_json JSON encoder, printable Unicode literal, slash and HTML punctuation unescaped |
| Ordered arrays | Existing order | Scenario steps retain execution order; sets/coverage lists use the orders stated here; refused is sorted with full multiplicity; no sorting of semantic sequences |

The v5 numeric/string spelling is tied to the inspected encoder behavior, not to a vague "whatever JSON library is current": Cargo.lock pins serde_json 1.0.151 and zmij 1.0.23. A dependency change that changes output fails byte fixtures and requires an intentional format decision. The implementation must pin golden vectors for 1.0, -0.0, fractional/exponent boundaries, Unicode combining sequences and escaped control characters before releasing a writer. This document does not claim those vectors have run. [S3; crates/specify/ess-primitives/src/node.rs:35–57 and facts.rs:22–61]

Readers admit valid noncanonical JSON spellings only after complete version/schema/semantic checks and duplicate-key detection; their exact digest remains the digest of the admitted original bytes. Thus a reader need not implement another language's canonical formatter to verify identity. For in-memory Rust suites, serialize once into an immutable byte buffer, admit/hash that buffer, and execute the corresponding admitted value. For Go, hash the complete embedded suiteJSON bytes before decoding into execution views; retain/validate the full envelope and coverage/dependency fields even if execution does not consume them. Never marshal the existing reduced Suite struct to calculate identity. Browser code retains response bytes before JSON parsing and verifies the selected suite/model before replay. [S4, S5, S8]

New report and detailed-report writers use the same v5 layout/scalar rules, including exact u64 timestamps as defined below, for their own bytes, but their hashes, if any, are report-artifact hashes and never substitutes for SuiteReference.digest. Existing realization artifact digests retain their original profile. [S10]

## New standalone report: ess-conformance-report/2

The closed object has the following fields; all are required. Unknown fields, unknown enum values, duplicate object keys, invalid numeric ranges and contradictory claims refuse admission. No v1 field is repurposed: v2 replaces the ambiguous flat failed count and status-prefixed list.

| Field | Meaning |
| --- | --- |
| format | Exactly ess-conformance-report/2 |
| specification, spec_digest, implementation | Existing label/model-digest/implementation meanings; spec_digest stays the existing 64-hex model digest |
| producer_profile | rust-scenario-status/1 or go-scenario-status/1, preserving the execution rules above; not a compiler build version |
| suite | SuiteReference for the exact document executed |
| execution_status | passed, failed or inconclusive, derived solely by the selected producer profile |
| counts | Exactly total, passed, failed, error, unsupported, skipped; nonnegative u64 |
| outcomes | Exactly passed, failed, error, unsupported, skipped; each is a sorted/distinct array of plain ScenarioIds, with no status prefix |
| coverage | {knowledge: unknown} for legacy suites, or {knowledge: complete_inventory or unknown, selection, counts, refused} copied exactly from the admitted v5 suite; refused is the full list with multiplicity, including effect, retained identity, scope and needs, so repeated and outside refusals remain visible |
| conformance_status | passed, failed or inconclusive under complete-selection/1 below |
| policy | Exactly complete-selection/1 |
| completed_at | Exact nonnegative epoch-millisecond u64, 0 through 18446744073709551615 inclusive, under the new timestamp rules below |

**New report/run timestamp contract.** Every timestamp in report/2 and run/2 is a nonnegative epoch-millisecond integer in **0..=18446744073709551615**. This covers standalone completed_at, detailed started_at and summary.completed_at; any timestamp inside a detailed result follows the same rule. On the JSON wire use an unsigned decimal integer token: 0 or a nonzero digit followed by decimal digits, with no sign, leading zero, fraction or exponent. Do not encode it as a quoted string or apply the binary64 payload-number profile. YAML presentation preserves the same exact integer and range.

Rust v2 writers retain the full Timestamp(u64) range. Go v2 wire fields use **uint64**, with a checked nonnegative conversion from the existing UnixMilli/int64 clock result; a negative clock value refuses v2 report production, emits diagnostics and exits nonzero without a complete report. It never wraps, clamps or silently switches to report/1. Clock values from 0 through i64::MAX convert exactly; the Go clock API's narrower production range does not narrow v2 reader admission of valid larger u64 values. This is a new shared contract, not a claim that the legacy producers already agree. [S11]

New readers, including browser consumers and AEP adaptation, parse timestamp integer tokens exactly before range checks. Their wire reader must preserve 0, 9223372036854775807 (i64::MAX), 9223372036854775808 (i64::MAX + 1) and 18446744073709551615 (u64::MAX) without passing through binary64 or silently narrowing to i64. A browser reader uses an integer-preserving parser/representation; ordinary JSON.parse followed by Number-based conversion is insufficient. A pre-parsed value whose original integer precision cannot be established is not qualifying input: require the original bytes and exact parsing, or refuse that route. If a downstream date/time type or API has a narrower domain, perform an explicit checked conversion and refuse that adaptation when out of range; the original valid u64 bytes remain positive and valid under this wire contract.

New reader and adaptation timestamp comparisons, subtraction, addition and duration conversions use exact checked integer arithmetic. Underflow, overflow or a narrowing conversion error refuses the affected report operation/adaptation instead of wrapping, truncating, saturating or qualifying a changed value. Negative values, values above u64::MAX and fractional/exponent/signed tokens are invalid v2 timestamp input, even when another numeric spelling would have the same mathematical value. The existing admission of noncanonical JSON layout does not relax timestamp token/range rules. None of these new rules changes v1 timestamp parsing, clocks, bytes or historical reader asymmetries.

counts.total = passed + failed + error + unsupported + skipped. Each count equals the corresponding outcomes array length; the five arrays are pairwise disjoint. Their union must equal the exact suite's selected scenario IDs. Rust requires skipped = 0; Go requires error = unsupported = 0. An unknown/mixed producer profile or an outcome inadmissible for that profile is a malformed v2 report, not an inferred translation.

counts.failed means only final failed scenarios. Rust errors and unsupported scenarios remain separate; Go's ordinary runner/target errors remain failed because that is its existing scenario result. The former v1 aggregate can be displayed as **non_pass = total - passed**, calculated with checked arithmetic, but is not stored as scenarios_failed in v2.

execution_status follows the frozen profile table. For a complete report, every selected scenario must have a terminal result. Cancellation, process termination, a host test filter that never invokes a selected Go subtest, or report I/O failure must not fabricate passed results for unexecuted IDs. Such an invocation may emit diagnostics, but cannot publish a complete v2 report. To run a subset and report it, select and bind a new explicit suite before execution; runtime filtering is not coverage selection.

complete-selection/1 determines conformance_status in this order:

1. execution_status failed yields failed, even if coverage is incomplete.
2. Otherwise execution_status inconclusive yields inconclusive.
3. Otherwise unknown inventory, any refusal with scope in_scope (including beside a selected or filtered-out scenario), or total = 0 yields inconclusive.
4. Otherwise it yields passed **for the declared selection only**.

An evidence consumer must additionally match its expected model digest, exact SuiteReference and selection. An authored-only passed result cannot satisfy a consumer asking for system generated_and_authored; a component passed result cannot satisfy a whole-system requirement. A report with unknown coverage is useful diagnostic history, never proof of complete coverage. Paired report admission recomputes counts/outcome-ID membership and v5 coverage equality, including the complete refusal occurrence list and its length, from the exact suite; structural report parsing alone must expose an unverified state and must not yield a qualifying evidence value.

No missing-suite or missing-coverage inference is allowed. Report v2 over legacy suite majors 1–4 is permitted for diagnostic category accounting when paired with its exact bytes; coverage is unknown and conformance_status cannot be passed. Report v1 is never silently upconverted to a qualifying v2 report.

## CLI surfaces, strict mode and version admission

Suite-producing verbs and conform run --path gain **--suite-format 4|5**; conform run gains **--report-format 1|2**. Generated Go selects the report with **ESS_REPORT_FORMAT=1|2**. These select versions, not JSON versus YAML. Loading a suite with --suite or embedding it in a Go package preserves its actual version; a suite-format option cannot relabel or downcast it. The frozen fresh legacy writer emits suite/4; existing suite/1–3 documents remain admitted byte-for-byte, not recreated by an invented old-major encoder.

Version and strictness selection is **independent, followed by a mandatory pairing check**. There is no automatic promotion to report/2 when a v5 suite or --strict is selected, and no automatic disabling of strict mode when report/1 is selected. Resolve explicit controls and defaults first, then apply the complete table below before target construction, identity lookup, callbacks or report writes. Rust and generated Go must implement the same check, even when no report destination was requested. A refusal explains the required explicit report/2 or diagnostic override; it emits no conformance report.

| Release phase of the CLI/generated runtime | Default fresh suite | Unset report selection | Unset strictness selection |
| --- | --- | --- | --- |
| Reader/opt-in writer releases, before default movement | suite/4 | report/1 | Diagnostic |
| Coordinated default release and runtimes generated from it | suite/5 | report/2 | Strict |

The runtime's generated release determines its defaults; an already generated Go package does not acquire new defaults by upgrading a separate ESS binary. Its embedded suite's version is still checked against the report it actually selects.

| Pair | Actual suite | Resolved report | Resolved mode | Required outcome in Rust and generated Go |
| --- | --- | --- | --- | --- |
| P1 | 1–4 | 1 | Diagnostic | Execute with frozen legacy output/count/exit behavior; no coverage qualification. |
| P2 | 1–4 | 1 | Strict | Refuse before execution: strict requires report/2; select report/2 or an explicit diagnostic override. |
| P3 | 1–4 | 2 | Diagnostic | Execute paired exact bytes; v2 categories with unknown coverage; conformance_status cannot pass. |
| P4 | 1–4 | 2 | Strict | Execute paired exact bytes; unknown coverage prevents success: failed execution yields failed, otherwise inconclusive; strict process exits nonzero. |
| P5 | 5 | 1 | Either | Refuse before execution, whether report/1 was explicit or default; require report/2. Neither allow-incomplete nor a missing report destination permits a v5-to-v1 downcast. |
| P6 | 5 | 2 | Diagnostic | Execute admitted exact selection; truthful v2 qualification, with producer execution exit behavior. |
| P7 | 5 | 2 | Strict | Execute admitted exact selection; process succeeds only for conformance_status passed and the expected selection. |
| P8 | Unsupported suite major or vocabulary | Any | Either | Refuse admission before execution, even if report selection itself is supported. |
| P9 | Supported suite | Unsupported report major | Either | Refuse report selection before execution. |
| P10 | Any | Any | Conflicting strict/allow-incomplete controls | Refuse invocation before execution. |

Thus during opt-in rollout a Rust run of suite/5 requires --report-format 2, and an upgraded Go runtime embedding suite/5 requires ESS_REPORT_FORMAT=2; leaving the report option unset selects report/1 and P5 refuses. Selecting --strict or ESS_CONFORMANCE_STRICT=1 during that phase also requires explicit report/2; it never silently changes the report format. These are configuration refusals rather than failed, skipped or zero-case conformance results.

The current conform run --format json/yaml output is the detailed S2 report, not S1 standalone output. Preserve that legacy structure and output bytes under report-format 1. For report-format 2, detailed output is a closed **ess-conformance-run/2** object with exactly format, summary, started_at, scenarios. summary is the complete v2 standalone report; started_at and summary.completed_at obey the exact u64 timestamp rules above. scenarios is the existing ordered detailed scenario-result sequence with the chosen producer vocabulary, whose IDs/statuses must agree with summary.outcomes. JSON/YAML is presentation of that object; --report-out always writes the standalone JSON summary. No consumer may identify the surface solely from --format json. Update help, fixtures and downstream detailed-output consumers before switching defaults. Go produces only standalone output; browser replay produces neither form.

Strict mode is **--strict** for the CLI and **ESS_CONFORMANCE_STRICT=1** for generated Go. It requires report v2 and a paired exact suite. It succeeds only for conformance_status passed and the caller's expected selection. In strict Rust mode, exits are 0 for passed, 1 for failed, 3 for inconclusive; admission/refused input exits nonzero before target execution. In strict Go mode, an inconclusive report must fail the enclosing test run even if all subtests were skipped. Report-format 1 retains its historical execution/output behavior only in an admitted diagnostic pairing (P1); a strict/v1 configuration is refused before execution (P2/P5).

Opt-in v2 without strict mode may execute incomplete/legacy selections diagnostically and return the producer execution exit behavior; its conformance_status remains truthful. **--allow-incomplete** or **ESS_CONFORMANCE_ALLOW_INCOMPLETE=1** explicitly chooses diagnostic mode in either release phase. Once suite/5, report/2 and strict become defaults, selecting legacy report/1 alone still resolves strict and refuses. The complete legacy opt-out is an actual suite/1–4 plus --report-format 1 --allow-incomplete, or the corresponding Go package with ESS_REPORT_FORMAT=1 and ESS_CONFORMANCE_ALLOW_INCOMPLETE=1; fresh legacy production also selects --suite-format 4. An actual v5 suite remains incompatible with v1 under every override. A v2 report over a legacy suite may be run in default strict mode (P4) but cannot succeed; --allow-incomplete selects its diagnostic P3 behavior. Explicit strict and allow-incomplete controls together refuse. Go's strictness controls accept only unset or 1; other values refuse as invalid configuration. The diagnostic override never changes qualification fields or bypasses version admission.

Before any target callback, every new reader must check exact supported membership, vocabulary appropriate to that suite major, closed envelopes, duplicate keys/IDs, semantic invariants, and expected byte digest where supplied. The admitted-execution supported set is 1, 2, 3, 4, 5; a syntactically valid 6 or 99 is refused. This set does not enlarge the frozen report/1 suite allowlist, which remains 1–4. Known newer steps under a falsely older major are refused. Legacy fixture admission remains version-specific and keeps the earlier meanings/omissions; legacy Node payload maps remain open data. Unknown typed fields on legacy input are refused by the new admitted-execution path, although historical readers sometimes ignored them.

## AEP mapping, impact and cross-repository movement

AEP owns a new versioned evidence result and fact namespace for v2. Its old EssConformanceResult, ess_conformance.scenarios.failed and historical predicates retain their meanings. The new result must retain the five categories, execution_status, conformance_status, exact suite reference and declared selection. New qualification predicates require conformance_status passed, exact expected suite/model, matching selection and nonzero total. They must not merely replace the old failed count with the narrower v2 failed count. There is no automatic lossy downcast from v2 to the old evidence variant. This is a required AEP contract migration; the exact AEP schema/version is governed by its own ADR implementation, not invented as already shipped here. [A1–A3]

Both aep-ess-evidence::adapt_json and aep-cli::recorded_from_report require version dispatch. The planning route must report the correct category counts and coverage scope, preserve exact references, and state when it records only descriptive evidence rather than qualifying facts. Updating prose must not claim that a lifecycle records count now evaluates conformance predicates; that is independently owned AEP behavior.

Impact continues using semantic dependencies for invalidation. A v5 admitted-suite view supplies the same dependency graph plus its selection; missing coverage cannot be interpreted as an empty dependency set.
