# A specification names the `ess` release it is maintained with

ess#106. A specification records its language version (`format: ess/1`) and nothing about which
`ess` release validated and generated it. Releases differ in what they accept — 0.32.0 refuses a
flat `ends_at > starts_at` guard that 0.30.0 validated — and nothing says so when the installed
`ess` is not the one the repository was last worked with.

## The declaration

`ess-inputs.yaml` gains one optional field, `requires`, in a new format `ess-inputs/2`:

```yaml
format: ess-inputs/2
requires: ess 0.32.1   # an exact release
# requires: ess 0.32   # or a minor line: any 0.32.x
specification: [system.yaml, domains/invoice.yaml]
scenarios: []
```

| form | satisfied by |
|---|---|
| `ess X.Y.Z` | exactly `X.Y.Z` |
| `ess X.Y` | any `X.Y.*` |

Anything else — another tool name, a range, a pre-release, `latest` — refuses as a malformed
declaration. Components are decimal integers without leading zeros.

**Why a new format.** The `ess-inputs/1` reader is closed (`deny_unknown_fields`), so a `/1` reader
handed a `requires` refuses it. That refusal is the right behaviour for an older `ess` — it cannot
honour a pin it cannot read — but it is a change of the persisted envelope, and the repository rule
is that such a change is a new version. `ess-inputs/1` keeps its exact meaning: a `/1` document
carrying `requires` still refuses, naming `ess-inputs/2`.

## What `ess` does with it

The check runs wherever `ess` acquires inputs through an `ess-inputs.yaml`, before any selected
file is read.

| installed `ess` against `requires` | result |
|---|---|
| satisfies it | nothing |
| older (below `X.Y.Z`, or below the line `X.Y`) | refusal, exit 1: names the required release, this release, and `b10x upgrade` / `/ess:upgrade` |
| newer (above `X.Y.Z`, or above the line `X.Y`) | one warning on stderr per command, and the command continues |
| newer, with `--strict-requires` | refusal, exit 1 |
| no `requires` (or `ess-inputs/1`) | exactly today's behaviour |

`--strict-requires` is a global flag: it is accepted in every position and has no effect where no
`requires` is read. An older `ess` that predates `ess-inputs/2` refuses the manifest as an
unsupported format; it cannot do better, and it does not proceed.

## Generated output records its producer

Generated output trees carry a private `.ess-output` checkpoint. Its format moves to
`ess-output-state/2`, which adds one required field, `producer`: the `ess` release that last
published into the tree, as `ess X.Y.Z`. The reader accepts `/1` (no producer) and `/2`; a
publication writes `/2`.

When a publication changes the tree and the recorded producer is a different release, `ess` prints

```
note: <root> was last generated by ess A.B.C; this is ess X.Y.Z, so a difference in it may come from the release
```

on stderr, so a diff in generated files can be attributed. A `/1` tree has no recorded producer and
prints no note; its first changing publication records one. A regeneration that changes nothing
writes nothing and says nothing. Recovery and adoption keep the producer they found.

An older `ess` refuses a `/2` checkpoint as an unsupported output-state version, and its generation
into such a tree refuses before writing. That is the same fail-closed direction as `ess-inputs/2`.
