## Optional kinds and draws

1. Extend `exploreKind` / `Kind` with `optional` holding its resolved inner kind. In `exploreResolveAs` / `resolveKind`, handle the IR Optional wrapper before the non-declared rejection, recurse with the same mode and incremented existing resource depth. Preserve the inner unsupported reason instead of replacing it with “optional”. Struct fields and declared newtype bodies already recurse: the same change must work at command roots and inside every struct nesting, including Optional<Optional<T>>. Retain the existing finite depth/cycle refusal; do not introduce a new shallower Optional limit.
2. Absence is a typed draw result distinct from a Node value, the existing no-record/redraw marker, and unknown reference-model knowledge. Use a small internal draw result carrying presence plus value; do not leak sentinels into target inputs, reports or histories. Each Optional layer consumes one `Chance(0.5)` draw, with the same polarity and PRNG consumption in both languages: first branch absent, otherwise recurse into the inner kind. The present branch uses the exact existing inner-kind algorithm. Nested wrappers remain observable only through their resulting values; they must consume the same deterministic draws in Go and TypeScript.
3. Carry field presence policy from the resolved field metadata in command and struct field plans. When a draw is absent, `null_when_absent` sends null, `omitted_when_absent` omits the property; with no explicit policy choose null as the canonical absent spelling. This is a fixed generation policy, not a new source meaning. An absent inner wrapper propagates absence to the containing field; it must not drop its containing present struct or a required sibling. Required nonoptional fields keep their current behavior.
4. Evaluate `defined`/`missing` with the existing predicate fact builder and evaluator over the actual drawn map. No ad hoc Optional guard parser. Tests must distinguish omitted/null Optional, empty text, false, zero, and empty but present aggregates according to the current predicate semantics. A genuine predicate Unknown must remain Unknown; do not turn it into missing or a default branch.
5. Preserve semantic knowledge of an explicitly drawn absent Optional when the model reads that input for a payload or stored assignment. An intentionally omitted, declared Optional field is known absent, not an unknown implementation choice. Introduce a narrow typed read helper or draw-plan lookup for `exploreValue` / `value`; do not treat every absent arbitrary path as known. Keep the existing optional/presence semantics for propagation, assignment and comparison. Compile fixtures for Optional copy into an Optional event/entity field and for nested omission before choosing the exact internal absent-value transition; neither absence nor unsupported expressions may become an invented scalar.

Known absence must remain known through the full observation path: payload comparison, model row writes/reads, view comparison and invariants. It must never be converted to `exploreUndetermined` or an undefined expected field that `exploreAgree` silently skips. The typed absent representation stays internal, while wire spelling follows the destination field's existing presence contract. For each healthy absent event, row and view control, a mutant fabricating a present value must fail. A missing unsupported path remains unknown rather than acquiring Optional authority.

The bounded correction must compose with every T already drawable in the same mode: supported primitives, enums, declared newtypes and structs. Concurrent-only drawable kinds remain concurrent-only. Optional around an unsupported List/Map/Union or other currently unsupported inner kind remains a precise inner-kind limitation; this unit does not silently accept it or discard its command without the original reason.

## Unknown-identity generation

Add a command-plan fact naming its explicit unknown-instance outcome and the existing resolved subject address. Preserve source identity/type information; no command-name inference.

For a command with a usable supplied subject and unknown-instance branch, the subject draw has explicit `known` and `fresh` modes. If no row exists, choose fresh without consuming an unnecessary mode coin. If rows exist, consume one shared `Chance(0.5)`: known chooses an observed row through the existing index draw; fresh invokes a dedicated fresh-ID helper. Commands without this marker preserve their current must-exist policy. Do not make every identity input fresh merely because another input is the subject.

The fresh helper draws a value of the same supported identity representation and checks it against the model's typed identity equality before use. Apply a bounded collision search, with the same candidate order/PRNG consumption in both runtimes. If the drawable domain is finite and exhausted or the existing attempt budget is exhausted, skip that draw while retaining truthful reachability accounting; do not exclude the whole command. Add collision and empty-domain controls. Never claim a merely newly sampled value is absent without checking it.

Keep known references as entity/creation-index provenance. Record fresh subject intent separately, including its entity and input path, so replay can validate it remains absent. A fresh literal is never converted to a known reference just because it later coincides with a target-generated ID. Optional absent values contain no reference; Optional present values retain every inner known reference at its complete field path.

## Source-selected outcome and effects

Allow `unknown_instance` through `explorePlanAs` / `plan`, without dropping the other condition/effect admission checks. Replace the current unconditional missing-record ambiguity only where source actually resolves it.

Preserve this sequence:

1. Input-guarded refusals retain their existing declared precedence, before subject lookup affects a result.
2. Evaluate the supported accepting guards/default/external alternatives using the existing selection rules. Do not globally return not-found solely because some other outcome has a supplied subject: a selected subjectless outcome still executes for a missing ID.
3. For each selected subject-requiring alternative, resolve its actual supplied address. If absent, take the source's explicit unknown-instance branch and its declared outcome/error/events/effects. Missing identity must not be classified as wrong-state or as an ordinary update. If present, retain the existing held-state/wrong-state path.
4. External eligibility and forced arrangement keep their existing meaning. An external subjectless branch can remain eligible; an alternative requiring a missing subject follows the source missing-instance resolution. Retain the selected alternative's original external arrangement identity separately from the resolved expected terminal outcome, as specified below. Deduplicate only choices equivalent in both arrangement obligations and expected semantics, preserving declaration order and shared random draws. A previously unsupported sibling branch remains explicitly unsupported, not silently interpreted.

Represent each executable alternative as an internal typed `Choice { arrangement, expected }`. `arrangement` is absent for an ordinary alternative or holds the original eligible external outcome handle/name that the target must be configured to force. `expected` is the terminal source-selected outcome after subject existence and lifecycle resolution. A missing subject can therefore produce `{ arrangement: externalUpdate, expected: unknownInstance }`; it does not change the arranged external cause. Retain source handles rather than command-name or ordinal inference. This metadata is private to the existing explorer assets, not a new callback or serialized format.

Thread this pair through Go `exploreDecision`, `exploreChoices`, the main loop, `explorePerform`, replay/shrink and reach accounting; TypeScript `Decision`, `choices`, main loop, `perform`, replay/shrink and reach accounting must match. Selection and PRNG ordering choose a `Choice`. External setup and forced-state eligibility use only `arrangement`; target verdict comparison and reference-model effects use only `expected`. Setup failure/unarrangeable reporting names the original arrangement. Reach accounting records the returned terminal outcome, and must not claim that the arranged external outcome was returned when execution redirected to unknown-instance. Reuse the existing expected-outcome effect machinery; never apply the original external update's effects to a missing row.

Trace `external` retains the original arrangement identity. Replay rebuilds current choices from source/model and matches the recorded arrangement against `Choice.arrangement`, then derives the expected terminal outcome again. It must not search for the external name in the redirected expected outcome. An ordinary choice and an externally arranged choice remain separate even if their terminal outcomes coincide. Two distinct external alternatives redirecting to the same unknown-instance result also remain separate: either may be unavailable or affect the target differently. Deduplication is allowed only when the arrangement identity/obligations and the full expected source semantics coincide; terminal outcome name alone is insufficient. Preserve any existing forced arrangement across consecutive calls according to its present rules.

A subjectless unknown-instance refusal changes no row and emits only what its source declares; a faulty target that mutates or emits an accepting event must disagree. If a source-admitted unknown-instance creation is within the existing effect/value profile, its actual creation result must update the model through the same existing effect machinery. Any broader upsert shape must first have an admitted compiled fixture and an identified source selection rule; do not introduce a new “unknown-instance must refuse” blanket restriction.

This ordering must be checked against the native source semantics using compiled minimal fixtures, especially a subjectless accepting/external alternative and an input refusal overlapping a missing identity. The old serial missing-record ambiguity masked these cases, so simply replacing it with an early return would be an incorrect fix.

## Replay, shrinking and concurrent recording

Copy drawn inputs with property presence intact. Existing known references continue resolving against the fresh target's recreated model; an unresolved arranger causes the replay step to be skipped as today. Before replaying a recorded fresh subject, verify its concrete identity is still absent. If removal/remapping makes it present, reject that candidate step/trace rather than silently changing its existence witness. Preserve the recorded external arrangement. The final shrunk failure must reproduce against a fresh target with the same affected command, absence/existence class and failed semantic check; do not accept an unrelated missing-record failure as the original one merely because both say “outcome”. Add a focused witness comparison for this feature if the current kind-only shrink test is insufficient; no general shrinker rewrite is intended.

The concurrent recorder shares `drawStep` and therefore gains Optional and fresh-ID inputs. Keep its prefix, workload, injections, retry correlation and actual callback input spelling unchanged. It does not use the serial model to judge concurrent outcomes. Test actual concurrent callbacks for absent/present and known/fresh subjects, inspect the recorded outcome/history, and call the existing checker/shrinker. Do not claim the existing history envelope retains input fields it does not record, and do not change that envelope to solve this issue. Related checker capability gaps are independent explicit limitations.

Concurrent workload inputs are drawn against the prefix model. `fresh` means absent in that snapshot only; another concurrent upsert may create the identity before the invocation executes. Such a call may correctly return update rather than unknown-instance. Do not apply the serial replay absence fence to concurrent execution or reject that legal race. Preserve actual target outcomes in the history and let the native checker judge their ordering. Concurrent replay/shrinking retains arrangement identity and actual observed outcomes without deriving a promised missing-row result from the earlier draw snapshot.
