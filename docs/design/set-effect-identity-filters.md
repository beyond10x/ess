# A set effect's filter reads the row's identity (`ess/27`); code targets owe set effects instead of refusing them

Status: design, not implemented (https://github.com/beyond10x/ess/issues/547). Source format
`ess/27`, which another unit opens (`FormatVersion::V27`,
`crates/specify/ess-domain/src/system.rs`; `V25` when written, before `ess/25` shipped); this design opens no format of its
own. No new keyword, no IR shape change, no new `ValidationCode`, no new suite step, no suite or
`ess-diff` version. It builds on `set-effects-over-filtered-instances.md` (the constructs and their
witness) and `filtered-related-reads.md` (the row-set selector, whose grammar it aligns with).

## The gap

A command expires a queue entry and, in the same outcome, ends the call the entry names. The entry
stores the call's identity in `call_id`. Two things stop an author:

1. **The filter of an `affects:` entry cannot read the row's own identity.** With the entry as
   subject, `where: call_id == subject.call_id` over the call refuses, although `call_id` is
   exactly the call's identity.
2. **Every code target refuses the whole workspace** for any `instances:` or `affects:`, so the
   other direction (the call as subject, its entries selected by `where: call_id ==
   subject.call_id`), which validates, synthesizes and passes the interpreter, still cannot be
   regenerated by a repository whose gate regenerates every target.

Minimal reproduction, `ess` 0.59.0 built at the integration head `3fdd9479e`, the specification
`a-identity-where.yaml` (two entities `demo.q.Call {call_id}` and `demo.q.Entry {entry_id,
call_id: CallId}`; `ExpireEntry` moves the entry and declares the `affects:` below):

```yaml
affects:
  - entity: demo.q.Call
    where: call_id == subject.call_id
    moves: demo.q.Call.end
```

```console
$ ess specify validate --path a-identity-where.yaml
a-identity-where.yaml was refused:
  - [unobservable_fact] command.demo.q.ExpireEntry.outcomes.expired.affects[0].where: `call_id` reads `call_id`, which is not a declared observable root
  - error[ESS-COMMAND-003]: `call_id` reads `call_id`, which is not a declared observable root
```

The same text with `== input.call_id` gives the same refusal, at `ess/26` and at `ess/27`.
`instance: subject.call_id` without `where:` is `ESS-COMMAND-004` (`instance:` names the row an
element of `each:` writes) and `ESS-COMMAND-005` (neither `where:` nor `each:`).

The reverse direction (`d-call-subject.yaml`: `EndCall` moves the call, `affects: [{entity:
demo.q.Entry, where: call_id == subject.call_id, moves: demo.q.Entry.expire}]`) validates;
`ess verify conform synthesize` writes 6 scenarios with 0 refusals; `ess verify conform run --target
interpreted --report-format 2` reports `6 scenarios: 6 passed`. Every code target exits 1:

```console
$ ess generate synthesize --path d-call-subject.yaml --target rust   # same for go, web, clap
rust target cannot emit this workspace
commands.demo.q.EndCall.outcomes.ended.affects: this target cannot change the rows a filter selects; a generated seam acts on the one instance its request names
```

The specifications named here (`a-…` to `j-….yaml`) were written for this design and are not
committed; every one is a variation of the two entities above, and U2's fixture is the
reproduction at `ess/27`.

The requester's proposals, labelled as theirs: (1) `where: <identity> == subject.<field>`, or
`instance: subject.<field>` without `each:`; (2) Rust and web generation of `affects:` over a
filter, or at least over one row named by identity. The issue names Rust and web; Go and Clap
refuse identically (output above).

## Why the filter refuses the identity

`affects:` and `instances:` check their filter over `&entity.fields`
(`crates/specify/ess-domain/src/command/set_effects.rs:1224-1242`, `check_filter`). The row-set
selector of `when_related: {entity, where, …}` and `{related: {entity, where, field}}` checks over
`row_set::candidate_fields`, which adds the identity and `state`
(`crates/specify/ess-domain/src/command/row_set.rs:240-251`). `filtered-related-reads.md` says the
selector uses "the stored-row predicate grammar already used by `affects:`"; for the identity it
does not. Measured: the same predicate as a row-set guard validates at `ess/24`
(`i-rowset-identity.yaml`, `when_related: {entity: demo.q.Call, where: call_id == subject.call_id,
exists: false}`: `valid`), and `ess/23`'s re-key collision answer is spelled `when_related:
{entity, where: <identity> == input.<field>, exists: true}` (`website/docs/reference/spec-versions.md`,
the `ess/23` row). The interpreter already puts the candidate's identity among a row's facts
(`crates/verify/ess-conformance/src/interpret/execute/set_effects.rs:352-369`), so only validation
stands in the way.

## Why every code target refuses

`set_effects::refuse` (`crates/generate/ess-synth/src/set_effects.rs:41-79`) fails the workspace for
every `instances:` and `affects:`, called from `lib.rs:421`, `rust/mod.rs:159`, `go/mod.rs:304`,
`web/mod.rs:303` and `clap/mod.rs:66`. It landed with the constructs on 2026-09-28 (`d790d6db9`),
one day before generated behaviour (`2066a0649`). Since then:

- `determined.rs:190-195` already keeps such a command an **obligation**, naming "effects on
  filtered rows (`affects:`)", and `tests/declared_behaviour.rs:533-536` pins that the plan says so.
- The seam an implementor writes takes only the input: `fn end_call(&mut self, input: EndCall) ->
  Result<EndCallOutcome, UnmetObligation>` (Rust) and `EndCall(input EndCall) (EndCallOutcome,
  *obligation.UnmetObligation)` (Go), from `ess generate synthesize` on `e-no-affects.yaml`. Nothing
  in it confines the behaviour to one row.
- The Clap target owes every behaviour by design (`clap/mod.rs:30-32`); the web bridge fills no
  behaviour (`web/mod.rs:23-30`).
- The sibling selector construct, a row-set guard, is an obligation, not a workspace refusal
  (`determined.rs:202-209`).

So the refusal's reason ("a generated seam acts on the one instance its request names") no longer
holds for an owed behaviour. The re-key refusal in the same function has a different reason (the
Go, Web and Clap seams write the row in place) and stays.

## Decisions

| # | decision | why |
| --- | --- | --- |
| D1 | From `ess/27` the filter of `instances:` and of an `affects:` entry reads the candidate row's identity, bare, as a row-set selector does. `state` stays unreadable there. | One grammar for "the rows of E where …" (`filtered-related-reads.md`); no new key; the requester's first proposal. `state` is not asked for and its witness interacts with a move's `from` states; it is named under "Not in this design". |
| D2 | `instance:` without `each:` stays refused; its hint names the identity filter. | `instance:` in `affects:` means create-or-update per element (`set-effects-over-filtered-instances.md`, #459). Reusing the key for "an existing row by reference" gives one key two meanings. |
| D3 | No `via:` in `affects:`. | It would be a third selection form next to `where:` and `each:`, an IR variant every consumer must learn, and about nine new refusals, and the filter grammar would still disagree with the row-set selector. |
| D4 | Rust, Go, Web and Clap emit a workspace for a specification with set effects; the command is an owed behaviour whose contract states the rows it changes. The re-key refusal stays. | Above: the refusal predates owed behaviour and contradicts `determined.rs` and the Clap and web designs. On its own this unblocks the reproduction's reverse direction on every target, at any format. |
| D5 | Generated Rust and Go behaviour executes an `affects:` entry whose filter **pins** the identity (below) through the storage port's `get`. Every other set effect stays owed, named. | A pin selects at most one row, read by identity as `when_related: {via}` already reads one (`rust/behaviour.rs:1682-1715`). An unpinned filter needs storage enumeration by a selector, which no generated behaviour has; it belongs to the story `ordered-related-head.md` proposes for row-set guards, filtered reads and the head together. |

## The construct

No new syntax. From `ess/27`:

```yaml
format: ess/27
# …
  - name: demo.q.ExpireEntry
    input:
      - {name: entry_id, type: demo.q.EntryId}
    outcomes:
      - name: expired
        moves: demo.q.Entry.expire
        instance: entry_id
        emits: [demo.q.EntryExpired]
        payload:
          demo.q.EntryExpired: {entry_id: input.entry_id}
        affects:
          - entity: demo.q.Call
            where: call_id == subject.call_id
            moves: demo.q.Call.end
      - {name: not-queued, wrong_state: true, error: demo.q.NotQueued}
```

**Reading.** In a set effect's filter a bare name is a field of the candidate row, now including
its identity. `subject.<field>` and `input.<field>` are as before. Identity comparisons keep the
`ess/22` rule: `==` and `!=` only.

**Meaning.** Unchanged from `set-effects-over-filtered-instances.md`: rows are selected from the
store before the outcome; only a filter that holds selects; a filter left unknown by an absent
Optional selects nothing; zero rows is an accepted answer; a selected row outside a move's `from`
states is skipped; the subject is excepted from an entry over its own entity; entries apply in the
order written. For the reproduction this means: a call already ended is skipped, a reference naming
no call changes nothing, an Optional reference holding nothing changes nothing. An author who wants
any of those refused declares the guard that says so, which already composes:
`when_related: {via: call_id, exists: false}` or `when_related: {via: call_id, predicate: state !=
Waiting}`. Both validate together on `ExpireEntry` at `ess/24`, with the outcome's `affects:` left
out, since `ess/24` refuses it (`j-related-guards.yaml`); that they compose with the entry is an
acceptance case of U1.

**A pin.** A filter *pins* the identity where it is `<identity> == <operand>` (either side), or a
top-level `all:` with exactly one such conjunct, and the operand is `subject.<field>` or
`input.<path>` typed as the entity's identity or `Optional<…>` of it. A pin selects at most one row.
Pins matter to synthesis and to generated behaviour only; validation and the interpreter treat the
identity as any other field.

## Validation

| case | code | at | message (hint) |
| --- | --- | --- | --- |
| the identity read in a set effect's filter below `ess/27` | `unsupported_format_version` | `…affects[<n>].where`, `…instances.where` | "`call_id` is the identity of `demo.q.Call`; a set effect's filter reads it from `ess/27`" (declare `format: ess/27`) |
| a pin over the subject's own entity whose operand is the subject's identity (`subject.<identity>`, or the input field the outcome's `instance:` names) | `conflicting_declaration` | `…affects[<n>].where` | the entry selects only the subject, which every `affects:` entry excepts (drop the entry, or write the change in the outcome's own `sets:`) |
| `instance:` without `each:` (existing) | `conflicting_declaration` (ESS-COMMAND-004) | `…affects[<n>].instance` | unchanged message; the hint adds: to change one existing row by its identity, write `where: <identity> == subject.<field>` (`ess/27`) |
| `state` in a set effect's filter (existing) | `unobservable_fact` (ESS-COMMAND-003) | `…where` | unchanged |

Below `ess/27` the refusal comes alone: the format check runs over the fields plus the identity, so
no `unobservable_fact` is reported beside it. This follows the gate `state` got in a related
predicate, refused below `ess/20` as `unsupported_format_version` rather than `unobservable_fact`
(`cross-record-and-stored-field-guards.md`, "Held state"). A message or hint change on an existing
site moves the pins named in `AGENTS.md` (`task test-xtask`, `cargo test -p ess-compiler --test
typed_diagnostics`).

## IR, schema, diff, generated documentation

- **IR.** No shape change. `ResolvedAffect::filter` and `ResolvedSetSubject`'s filter are
  `Predicate`s (`crates/specify/ess-compiler/src/ir.rs:1024-1048`) and may now name the identity.
  A model without such a filter keeps its bytes; `EssIr::format` records `ess/27`.
- **Schema.** `where:` is a written predicate string, so `schemas/generated/ess.schema.json` does not
  change.
- **`ess verify diff`.** `outcome-set-effect-changed` already prints the filter
  (`crates/verify/ess-diff/src/diff.rs:2880-2940`). No `ess-diff` version, as `ess/22`'s and
  `ess/23`'s new entry forms took none (the `ess-diff` rows of `spec-versions.md`).
- **Generated documentation.** `ess-gen/src/set_effects.rs:63-68` prints the filter. A pinned entry
  reads better as "the `demo.q.Call` whose identity is `subject.call_id`"; optional polish in U6.

## Interpreter and history checker

No change expected: `select` evaluates the filter over `row_facts`, which inserts the candidate's
identity (`interpret/execute/set_effects.rs:352-369`, `:371-421`). This is inferred from the code,
not run: U2's first test (`the_interpreter_moves_only_the_row_the_subject_names`) is expected green
once U1 admits the filter, and if it is red the fix is U2's. That the history checker reaches the
same `select` is inferred too, and U2 checks it; a pin whose operand is a generated value no
history recorded would stay undecidable, as any filter does today (`:410-418`).

## Synthesis

Today the `affects:` segment creates the subject first and writes its values into three selected
rows (`synthesize/set_effects.rs:1234-1410`), and already binds `subject.<subject identity>` and
`input.<field>` operands to captured instances (`affect_inputs`, `:1172-1232`,
`story:feature-request-288`). A pin reverses the direction: the selected row's identity is minted
by its own creation, so the row is created and captured first, and the subject is arranged to name
it.

For an `affects:` entry with a pin on `subject.<field>`:

1. Arrange the target row: in a `from` state of the entry's move (other than the arrival where one
   is reached), with each `sets:` field holding a value the effect changes, every other conjunct
   true. Capture it.
2. Arrange the subject so that its stored `<field>` holds the capture: through a command that writes
   `<field>` from an input (`QueueEntry` writes `call_id: input.call_id`), found by the same search
   the stored-reference `when_related` witness uses (`synthesize/related_guard.rs`). None found
   (the field is `{generated: true}`, or no command writes it): `NoWitness`, named.
3. Arrange a decoy of the same entity under another identity, satisfying every other conjunct and
   in the same state: it must read unchanged.
4. Send the command; read the target row changed and the decoy as arranged, through the row-level
   views the segment already requires (`:127-150`).
5. Further subject/row pairs, each with its own send: per other conjunct, a pinned row that fails
   it (unchanged); for a move, a pinned row outside the `from` states (unchanged, outcome still
   accepted); a subject whose `<field>` names an identity no row carries (accepted; the identity
   read absent with `expect_subject_absent`, so a target creating the row fails); an `Optional`
   `<field>` left absent (accepted, decoys unchanged). A pair no declared command reaches is left
   out, as the zero-match call is today.

A pin on `input.<path>` is the same with the capture sent as input. For `instances:` with a pin, one
selected row replaces the three; the zero-match call sends an identity no row carries, and
`{count: changed}` must read 1 and then 0, which still catches a constant. An identity read other
than as a pin (`!=`, inside `any:` or `not`, twice) gets a named `NoWitness`.

Steps used: `execute_command`, `expect_outcome`, `capture_instance`, `query_view`, `expect_view`
`contains`, `expect_subject_absent`. All exist, so no suite version is taken.

## Format and compatibility

- **Source `ess/27`.** Below it the identity in a set effect's filter is refused naming `ess/27`.
  At `ess/27` every `ess/26` document keeps its meaning and IR bytes: no document that validated
  before reads the identity there.
- **D4 changes generated output, not a format.** A specification that a target refused now emits a
  workspace and one obligation more. Nothing that emitted before changes.
- **Migration.** None. An adopter writes `format: ess/27` and the filter.

## Fit review

1. **Need.** A command changes, in the same outcome, the one record its subject refers to by a
   stored identity, or the record an input names. ESS cannot say it from the referring side, and no
   specification with any set effect can be regenerated by a code target. Reproduction: "The gap",
   `ess` 0.59.0 at `3fdd9479e`. The requester's syntax is quoted there, labelled.
2. **Class.** Part 1 is a **defect**: `filtered-related-reads.md` says the selector shares the
   set-effect filter's grammar, and the two disagree on the identity (`set_effects.rs:1224-1242`
   against `row_set.rs:240-251`; measured above). Part 2 is a **defect**: the workspace refusal
   contradicts the obligation `determined.rs:190-195` already plans, and the Clap and web designs
   (`clap/mod.rs:30-32`, `web/mod.rs:23-30`).
3. **Already expressible?** Only from the other side: with the call as subject (`d-call-subject.yaml`,
   valid, 6 of 6 interpreted). An adopter whose operation is keyed by the entry cannot turn it
   around without changing its API. `when_related: {via}` guards one related row
   (`f-related-guard.yaml`, valid) but changes nothing. A relation is not read by `affects:`
   (`set-effects-over-filtered-instances.md`, "Out of scope"). Code targets: no idiom; every set
   effect refuses.
4. **Fit.**
   - *Vocabulary.* No new key; the row-set selector's reading of a candidate row, already in use
     (`ess/23` collision answer).
   - *Composition.* Guards: `when_related: {via}` refusals on the same command validate at
     `ess/26` (`j-related-guards.yaml`); beside the entry at `ess/27` is a U1 acceptance case.
     Moves, deletes, `sets:`, subject exception and the zero-row rule are unchanged. `each:` is
     untouched. `{count: changed}` keeps its `instances:`-only rule.
   - *Siblings.* Set-effect filters and row-set selectors then differ only by `state` (named
     below).
   - *Targets.* Every target handles or names it (table above).
5. **Second adopter.** A booking system: cancelling a booking releases the seat it holds, `affects:
   [{entity: Seat, where: seat_id == subject.seat_id, moves: Seat.release}]`. A device registry:
   forgetting a token is idempotent, `deletes: Token` with `instances: {where: token_id ==
   input.token_id}`, zero rows accepted.
6. **Cost.** Format: rides `ess/27`. Keywords: none. Diagnostics: one new refusal site
   (`conflicting_declaration`), one format gate, one hint; no new `ValidationCode`. IR, schema,
   suite, `ess-diff`: none. Generated API: no breaking change; D4 turns a refused workspace into an
   emitted one. Synthesis: one arrangement path.
7. **Alternatives.**
   - (a) **Change nothing.** The adopter keeps the operation on the call side and cannot regenerate
     any target.
   - (b) **D4 alone.** Unblocks the reverse direction on every target today. Leaves the selector
     grammar inconsistent and the entry-keyed operation inexpressible. Taken, as unit U3, but not
     alone.
   - (c) **`via:` in an `affects:` entry** (`{entity, via: call_id, moves: …}`, reusing
     `ResolvedRelatedVia`). Rejected (D3).
   - (d) **`instance: subject.<field>` without `each:`** (the requester's second spelling).
     Rejected (D2).
   - (e) **Identity in the filter** (the requester's first spelling). Chosen, with `state` left out
     and the pin rule for synthesis and generation.

## Disagreements

No story was planned for this issue before this design. One existing decision changes:
`set-effects-over-filtered-instances.md` says Rust, Go, Web and Clap "refuse both by name as
`MissingRepresentation`" (sections "Related-record moves", "Deleting the selected rows", "One row
per element", "Targets"). D4 replaces that with an owed behaviour; U3 edits those paragraphs and
the tests that pin the refusal (`ess-synth/tests/set_effects.rs:26-164`). This is a reversed
decision, not a weakened check: each rewritten test asserts the obligation and its contract
instead.

## Not in this design

- **`state` in a set effect's filter.** Its witness must arrange rows by state against the move's
  `from` states. No need has been stated.
- **Generated enumeration of unpinned filters, `each:` and `instances:`.** It joins the selector
  enumeration story `ordered-related-head.md` proposes.
- **`affects:` across a declared relation by name**, and the issue's fourth attempt (a second
  relation over the field an `owns` relation carries). Neither is needed once the filter reads the
  identity.
