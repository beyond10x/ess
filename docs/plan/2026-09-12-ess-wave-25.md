`the-startup-lock-does-not-cover-the-first-round-trip`, `a-marked-region-is-not-a-scan-of-what-runs`,

either discarding that branch's work or merging it, and neither is this wave's to decide.

**One candidate failed the blast-radius property, measured.**

**159 `ValidationError::new` sites across 53 files.** Its own body said it was not a wave candidate
until scoped; now it is scoped and the number says the same thing.

**Three were excluded on the first property, implementable tonight.**

`scrub-the-planning-store-or-say-why-not` is store mutation, which the protocol reserves to the

**Two were excluded for inferred scope.** `create-only-command-cannot-refuse` and

until somebody scopes them.

### Why unit 1 is first

It is the wave-24 gate's one red lane, and it is red on `main`:

```
duplicate concrete consumer entry
ess_domain::lib(ess_domain)::binding::periodic::macro::invocation/profile_word
```

`consumer_coverage/consumer.rs:317` computes an invocation's distinguishing `/for/<x>` suffix for
exactly one hard-coded macro name and leaves it empty for every other, so any macro invoked twice in
one module collides. Until it is fixed no wave can close on a fully green gate.

## Closing the wave

`task check`, step by step. **`ess-xtask` is a separate step**: `task test` runs
`cargo test --workspace --exclude ess-xtask` and then a second invocation under a pinned profile
(`RUSTUP_TOOLCHAIN=1.98.1`, wrappers unset, debug and incremental zeroed). A per-package substitute
misses it, and that omission when wave 22 closed is how the `layout` regression reached `main`.

A `review-result` is immutable: its ```findings``` block has to be present when the record is
created, because it cannot be added afterwards.
