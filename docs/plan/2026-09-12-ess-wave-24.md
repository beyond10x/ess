## A store rule this wave learned

`review-result` is immutable — `aep.review-result/v1` refuses a body replacement with "a record that
can be edited after the fact is not evidence". So a ```findings``` block has to be in the record
**when it is created**; it cannot be added later. Two of this wave's records were written without
one, which means `aep plan artifact findings` cannot build a carried/new/resolved ledger from them.
`review-result:adversary-wave24-unit3-pass-1-findings` supersedes one of them with the same findings
in enumerable form. Unit 2's pass-2 record has no supplement; its ledger is moot because the unit
left the wave.

### The one red lane, and why the wave merged anyway

```
duplicate concrete consumer entry
ess_domain::lib(ess_domain)::binding::periodic::macro::invocation/profile_word
```

`consumer_coverage/consumer.rs:317` computes an invocation's distinguishing `/for/<x>` suffix for
exactly one hard-coded macro name — `checked_deserialize` — and leaves it empty for every other, so
any macro invoked twice in one module collides. `profile_word!` is defined at
`ess-domain/src/binding/periodic.rs:72` and invoked eight times from `:92`.

Measured at both commits with the identical message: `ab2bb7f1` and **base `bd722fa9`**. The wave's
diff touches no file under `binding/`, no consumer-coverage input, and contains 0 occurrences of
`profile_word`. It arrived with `periodic.rs` in `9572af9b`; wave 23's recorded exits carry no
`consumer-check` line, so the lane was not run at that close either.

Merging into a lane that was already red does not make it redder, and holding every wave until
somebody fixes a defect no wave caused stops the loop. That is a judgement, and it is in the merge
commit rather than left to be inferred.
`story:a-macro-invoked-twice-in-one-module-refuses-the-consumer-gate` carries it.
