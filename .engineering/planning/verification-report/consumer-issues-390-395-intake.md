## 390: broker, stream and retention

Need: a publisher's event delivery contract identifies its broker address, capture stream, retention and the producer's lack of provisioning authority. This is a gap, not a defect in current AsyncAPI: ess-gen/src/asyncapi.rs:3–13 explicitly states that the model has no transport construct and cannot emit servers/bindings. EventSpec is an immutable domain fact with fields/naming only (ess-domain/src/command.rs:3910–3922). Component reach explicitly excludes protocol selection (component.rs:208–222). The configuration epic explicitly records two prior transport-DSL declines (.engineering/planning/epic/configuration-declared-once.md:49–54), though this intake did not recover those original individual decisions.

Proposal: defer the proposed `transports` source syntax pending one explicit boundary decision: does broker delivery live in semantic ESS or a separately typed realization/deployment contract? Preserve events as facts; do not put NATS provisioning beside event fields merely because this adopter proposed it. Alternatives: change nothing/prose (does not check the contract); add event-level provider syntax (conflicts with existing boundary); separate typed transport binding keyed by component publication and event identity (preferred design direction). A second example is an audit publisher sending to a retained Kafka topic without topic-creation permission. Narrow next scope: design this authority seam and its reference/retention semantics, then AsyncAPI/docs/diff/schema readers together. New authored envelope/version cost is real; no version selected here.

## 391: address templates and typed token bindings

Need: publication address parts come from typed event fields or supplied publication context, with protocol token constraints. Gap: asyncapi.rs:15–35 projects literal naming.wire or a qualified name; existing consumer delivery context is not publisher address authority. Existing configuration epic excludes a generic template language (:62). No duplicate identified.

Proposal: accept redesigned as a finite, typed publication-address binding under the boundary selected for 390; do not reinterpret literal naming.wire or overload consumer delivery context. Specify field access, context ownership, escaping/refusal and missing facts before generation. Alternatives: prose/literal per-producer events (cannot express dynamic routing); generic string templates (unbounded and duplicates mapping rules); typed address segments reusing resolved field access (preferred). A second example is per-tenant audit routing. Narrow scope includes source/compiler validation, AsyncAPI parameters and protocol constraints, docs/diff and actual producer tests. All runtime targets must carry the same binding or explicitly refuse during initial design qualification; the user's full-runtime release requirement still applies. New source meaning needs a coordinated version, ideally the same unreleased transport unit rather than one bump per issue.

## 392: batched wire envelope

Need: each item remains the event fact while one broker message carries a JSON array of those facts. Gap: EventSpec fields form the record, and AsyncAPI schemas reuse `types::Message::of_event` (asyncapi.rs:1062–1075; types.rs:920–930), which describes one event payload. List-valued event fields can describe an object containing a list; that is not the requested top-level array wire contract.

Proposal: accept redesigned as a publication-envelope capability at the same transport/realization seam as 390, preserving the domain event's shape. Alternatives: keep object payload and change the consumer wire protocol (does not meet existing contract); change every event into a list-root value (confuses one fact with its delivery batch and broadens every outcome/binding); typed singleton/batch wire envelope around existing payload projection (preferred). Second example: batched sensor readings where individual readings still drive bindings. Narrow scope includes batch identity/order, empty-batch semantics, delivery acknowledgement/failure granularity, shared schema/AsyncAPI and publishers; must settle these before claiming 395 can batch safely. Version cost belongs to the envelope contract, not a silent change to existing event schemas.

## 393: generate an existing event payload as a data type

Need: realize an already-declared event payload once without duplicating every field into a named struct. Gap in type selection, not a need for a new event payload syntax. `ModelTypes::select` only searches ir.types (ess-gen/src/model_types.rs:35–59), while the shared generator already maps event payloads (types.rs:920–930). Types-only design explicitly selects named type roots (docs/design/types-only-realizations.md:16–43).

Proposal: accept redesigned by adding typed event-root selection to the existing sealed ModelTypes/schema-contract realization path, with no new authored ESS event key. Event and type names are only unique per kind; AsyncAPI explicitly preserves separate `event.` and `type.` schema namespaces (asyncapi.rs:85–90). Therefore avoid ambiguous implicit `--root NAME` precedence; expose an explicit event selector or kind-qualified selector while preserving old type roots. Alternatives: current duplicated structs (drift remains), authored `payload: Struct` (permanent new language surface), selecting existing event payload (smallest). Second example: an audit event library shared by independent publishers. Narrow scope: root kind/provenance, reachable type closure, collisions/wire names, exact generated Go/Rust/TypeScript data/codec tests, CLI docs. Reuse shared schema mapping; report model constraints honestly. Persisted report root identity may need a version decision; no authored-format bump required merely for selector capability.

Alternatives: change nothing (validator still accepts forbidden data), new Int32/Int64 primitives (duplicates expressible constraints), shared invariant lowering (preferred). Second example: packet sequence bounds and an exact protocol-version field.

## 395: generated publishers

Need: a typed component publisher connects, encodes the declared message/address, publishes and reports batch failures with truthful delivery semantics. Gap: the current type-only contract explicitly excludes services/applications/executors (types-only-realizations.md:3–6); generated data types alone cannot implement broker authority. Proposal: accept redesigned as a typed publisher realization consuming resolved component publications plus the explicit transport/address/envelope decisions in 390–392, without pretending the existing client generation already contains those facts.

Alternatives: hand-written adapter (possible but no generated consistency), immediately add `generate client --target go|rust` with guessed NATS defaults (silently invents authority), plan a typed publisher adapter over the agreed realization contract (preferred). Second example: a durable audit producer. Narrow scope must define connection authority, no provisioning unless separately granted, exact address/envelope encoding, acknowledgements/retries, partial-batch failures and delivery guarantees; produce actual generated Go/Rust behavior tests against a controlled broker/port and independently broken implementations. Integration with existing component publishes.events should be reused. Generated public API/new target cost exists even if no new semantic source syntax is ultimately needed. Record dependency on 390–392 and 393 explicitly; do not count this issue as satisfied by emitted `publish` method names alone.
