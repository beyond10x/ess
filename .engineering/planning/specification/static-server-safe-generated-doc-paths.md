# Specification: Static-server-safe generated documentation paths

## Context

This record migrates `beyond10x/ess` GitHub issue 2, “ess generate --kind docs emits filenames a static server cannot serve.” The issue was opened by `timofriedlberlin` on 2026-09-02 at 14:12:51Z, remained open with no labels, assignees, milestone, or comments, and described dotted domain names becoming dotted path segments that static servers interpret as extension-bearing filenames.

No implementation was added during this migration. Current `main` already satisfies the issue through commit `6cd3706ee2530a1806e74f169851d23667b2bdb7`, released in ESS 0.4.0 and every later release through 0.9.2. The implementation explains and performs the transformation at `crates/ess-gen/src/docs.rs:2502-2511`; generated-document tests exercise hyphenated domain paths beginning at `crates/ess-gen/tests/docs.rs:308`.

## Requirements

1. A domain page generated by `ess generate --kind docs` uses a static-server-safe path stem.
2. Every dot in the qualified domain name becomes a hyphen in the path stem, so `acd.routing` is emitted as `domains/acd-routing.md`.
3. Links generated for that domain use the same transformed page identity.
4. The page content and title retain the qualified domain name; only its route identity changes.

## Constraints

- The transformation is deterministic and does not depend on a particular static-site generator.
- The generated Markdown extension remains `.md`; only dots within the route stem are transformed.
- A consumer must not need a post-processing rename-and-rewrite pass.

## Out of Scope

- Choosing a documentation site theme or static-site framework.
- Renaming the domain inside the ESS model.
- The broader `--kind site` projection that landed in the same implementation commit.

## Invariants

- A qualified domain name maps to one stable page identity everywhere the generator writes or links it.
- A route stem generated from a dotted domain contains no dot.
- Repeated generation from the same ESS IR produces the same paths and links.

## Acceptance Criteria

- Generating documentation for `acd.routing` produces `domains/acd-routing.md`, never `domains/acd.routing.md`.
- Every link targeting the generated page resolves to the hyphenated path.
- `task check` passes at the migrated repository revision.

## Resolution

Implemented before migration by `6cd3706ee2530a1806e74f169851d23667b2bdb7` and included in the published 0.4.0 release. This migration records the already-delivered behavior; it does not build it again.

## Ambiguities

- `inferable` — the requested filename mapping is explicit in the issue and in `domain_page_id` at `crates/ess-gen/src/docs.rs:2509-2510`.
- `inferable` — the behavior is released: `git tag --contains 6cd3706` includes 0.4.0 through 0.9.2.

## Original GitHub Issue

Source: `https://github.com/beyond10x/ess/issues/2`

> `ess generate --kind docs` writes one page per domain, named after the domain. A domain called
> `acd.routing` becomes `domains/acd.routing.md`, and the site built from it serves
> `domains/acd.routing/`.
>
> A static file server reads the dot as an extension boundary and returns 404 for that path. This is
> not a Docusaurus quirk — GitLab Pages, GitHub Pages and `http-server` all behave this way, because
> the segment looks like a filename.
>
> **Observed** on `sbf/acd`, whose ESS model declares `acd.routing` and `acd.backend`. The published
> site 404s on both domain pages until the stems are renamed and every link to them rewritten. The
> repository carries that rename as a post-processing pass in `scripts/build-docs.sh`, which is a
> workaround every consumer of `--kind docs` with a dotted domain name will have to write.
>
> ### What would fix it
>
> Emit the dot as something a path segment can carry — `domains/acd-routing.md` — and write the links
> to match. The page's title still says `acd.routing`; only the filename changes.
