## Need

An `ess-cli` binding cannot present two common command-line shapes: a valueless boolean switch
(`run --net`) and an option given once per list element (`run --ro /a --ro /b`). Today a Boolean
option needs an explicit value (`--net true`) and a `List<T>` option takes one JSON list and refuses
a second occurrence, so a hand-written CLI that offers the usual shapes is a superset of its binding.
The `--target clap` synthesis already renders a list field as a repeated flag
(`crates/generate/ess-synth/src/clap/tree.rs:136-157`), so the two CLI projections disagree.

Reproduced on 0.92.0 with a minimal model (`demo.client.RunRequest`: `net`, `ro`, `argv:
List<String>`; one command `run`):

```console
$ ess specify cli --path flag --binding flag/cli.yaml
error: commands[0].arguments[0].source.kind: unknown variant `flag`, expected one of `option`, `positional`, `document`, `protected`, `trailing` at line 19 column 37
$ ess specify cli --path repeat --binding repeat/cli.yaml
error: commands[0].arguments[1]: unknown field `repeated`, expected `long` at line 20 column 9
$ ess specify cli --path trailing --binding trailing/cli.yaml
error: a trailing source binds a required List<String> field
```

## Acceptance

- `docs/design/cli-presentation-binding.md` documents `{kind: flag, long: <name>}` and
  `{kind: option, long: <name>, repeated: true}` beside the other sources, with the rules below and
  the format consequence (no format change, as for `trailing` in 0.54.0).
- `ess specify cli` accepts `{field: net, source: {kind: flag, long: net}}` over a required
  `Boolean` (a newtype over one counts) and refuses it over `Optional<Boolean>` or any other type,
  naming the field and that absent and `false` would be two spellings of one value.
- `ess specify cli` accepts `{field: ro, source: {kind: option, long: ro, repeated: true}}` over a
  required `List<T>` and refuses it over `Optional<List<T>>` or a non-list field, naming the field.
- A CLI generated by `ess generate cli` from such a binding parses `run --net --ro /a --ro /b -- x`
  into `{"net": true, "ro": ["/a", "/b"], "argv": ["x"]}`, `run` into `{"net": false, "ro": [],
  "argv": []}`, and `run --ro '["a"]'` into `{"ro": ["[\"a\"]"]}` for `List<String>` (each
  occurrence read by the element rule: text for String/newtype/enum, JSON syntax otherwise); a
  binding without the new source and key generates byte-identical packages.
- The refusal of a trailing source over another type names the reason and the idiom: "a trailing
  source binds a required List<String> field; no `--`, or nothing after it, is `[]`, so declare the
  field `List<String>` rather than `Optional<List<String>>`".

## Fit review

1. **Need.** A CLI binding should present a boolean switch and a per-occurrence list option, the
   two shapes most command lines use for "on/off" and "many paths". Proposal (theirs): `kind:
   flag`, present `true` and absent the field's absence over `Optional<Boolean>`; `repeated: true`
   on an option over `List<T>`; and for gap 3 either admit `Optional<List<String>>` on a trailing
   source or make the parser refuse a missing argv.
2. **Class.** Gaps 1 and 2: gap (no source can present either shape; `run.txt` § 1, § 2).
   Gap 3: neither defect nor gap: the design states that no `--` gives `[]` and refuses the
   optional list because absent and empty would be two spellings
   (`docs/design/cli-presentation-binding.md:206-215`, `resolve.rs:368`); the parser and binding
   agree.
3. **Already expressible?** Gap 1 and 2: only as `--net true` and one JSON list (`run.txt` § 0,
   issue output), not the established command line. Gap 3: yes, required `List<String>` with `[]`
   meaning "no command" (the idiom, `idiom.md`).
4. **Fit.** No source-language cell (`docs/design/language-grids.md` grids R and O do not cover
   bindings). `flag` is a new source kind beside `trailing`, added the same way; `repeated` is a
   property of the existing `option`. Both follow the trailing rule that one value has one
   spelling, which is why `flag` binds a required `Boolean` (absent = `false`) and `repeated` a
   required `List<T>` (absent = `[]`), not the `Optional` forms asked for. "Repeated" is the word
   ESS already uses for this CLI shape (`CHANGELOG.md:2900`, clap target). Every reader handles
   it: the contract (`wire.rs`, `resolve.rs`) and the one generated target (`runtime.rs`); an
   older reader refuses the kind and key by name (serde `deny_unknown_fields`, `run.txt`).
5. **Second adopter.** A backup tool: `backup --verbose --exclude '*.tmp' --exclude cache/ --
   /srv`.
6. **Cost.** No format change: `ess-cli/1`, `/2` and `ess-cli-plan/1`, `/2` gain a kind and a key
   as they gained `trailing` in 0.54.0 (`docs/design/cli-presentation-binding.md:257-261`);
   generated packages drift until regenerated (`ess generate cli --check`). No new diagnostic
   code (the contract refuses with text). No migration.
7. **Alternatives.** (a) Change nothing: the hand-written CLI stays a superset, refused. (b) The
   requester's `Optional<Boolean>` flag: `false` could never be sent, and absent and `false`
   would both mean "off"; refused. (c) Make every `List<T>` option repeat: changes the meaning of
   existing bindings; refused. (d) Admit `Optional<List<String>>` on trailing: two spellings of
   one value, refused by the design already. Chosen: (e) `flag` over `Boolean`, `repeated: true`
   over `List<T>`, a clearer trailing refusal.

## Decisions

Gaps 1 and 2: accept, redesigned. `kind: flag` binds a required `Boolean` (absent is `false`),
not `Optional<Boolean>`; `repeated: true` on `option` binds a required `List<T>` (absent is `[]`).
Gap 3: decline, with the idiom: declare the trailing field `List<String>`; no `--` hands `[]`,
which the handler reads as "nothing to run" (`idiom.md`); the refusal names that idiom.
