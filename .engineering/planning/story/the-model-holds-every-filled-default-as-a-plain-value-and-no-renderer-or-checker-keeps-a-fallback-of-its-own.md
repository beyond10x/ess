## Need

**Not part of P0's delivery.** This is a draft follow-up: the resolved document is complete
without it, and the requester is not affected.

After the P0 fill units, the loader writes every default into the tree, but the model still types
most of them as `Option<T>`, and each renderer still carries the fallback it used before, now dead
code. The table of `g03-loader-fills-defaults` lists them. Among them:

- `collection.style`: `crates/ui/ess-ui-react/templates/runtime/composites/collection.tsx.tmpl:116`,
  `:541`; `crates/ui/ess-ui-tui/src/view.rs:1414-1415`; `crates/ui/ess-ui-test/src/parity.rs:84-85`.
- `Document.actor`: `crates/ui/ess-ui-react/src/emit.rs:3322-3325`.
- `when_paged_away`: `crates/ui/ess-ui-tui/src/app.rs:2511-2516`.
- `rich_text.syntax`: `rich_text.tsx.tmpl:21`, `view.rs:1221`.
- `confirm.confirm_label`: `confirm.tsx.tmpl:131`, `view.rs:2417-2420`.
- The store resolution of React (`emit.rs:366-445`), the terminal (`placement.rs:82-126`) and the
  checker (`ess-ui-check/src/rules.rs:1392-1433`). Each now takes the written store at its first
  step (`g03-placement-in-loader`).

A fallback that stays will one day disagree with a changed schema default again, which is how the
disagreements of P0 arose. The earlier draft's acceptance said: "`Document` holds the same values,
and no renderer keeps a fallback of its own."

## Outcome

- Every model field whose row in the table of `g03-loader-fills-defaults` says **always** is a
  plain `T`, not `Option<T>`.
- Every field whose row names a condition stays `Option`. The list is read from that column and
  repeated in the test:
  - `Field.unit`, `Field.scale`, `metric.unit`, `metric.scale` (by `as` or `format`);
  - `form.fields` (with a model);
  - `State.store`, `State.scope` and `Reads.cache` (where resolution yields a store);
  - `Reads.key` and `Live.match` (not on a choice's read);
  - `Field.tone` (beside a `tone_by`);
  - `Live.when_paged_away` (on a section `live` block);
  - `NavEntry.label` (where the page writes `nav:`);
  - `Reads.pager.sizes`, `Header.badge.tone`, `Field.label_from.key` and
    `Field.suggests.value` (where their parent is written).
- Every renderer, emitter, template and checker reads the field directly, and its own fallback is
  deleted. In the React templates, a `?? <default>` on a prop the emitter now always passes is
  deleted too.
- The three store resolvers are reduced to reading the written store, keeping their refusals.
- No behaviour changes and no generated byte changes, apart from the deleted template fallbacks.

## Fit review

Read at tree `bcfc51555`. It follows from report item 3 and the owner's order "the loader fills
every default": one table, in the schema, applied once.

1. **Need.** No second copy of a default exists anywhere.
2. **Class.** It is maintenance of a *gap* fix: it keeps the defects fixed in P0 from coming back.
3. **Already expressible?** Not applicable.
4. **Fit.** No authored surface and no format.
5. **Second adopter.** Every future change of a schema default, which is then one edit.
6. **Cost.**
   - A wide mechanical diff across six crates, which conflicts with every open story that edits
     the same fields.
   - A Rust API break for downstream users of `ess-ui`'s model.
7. **Considered.**
   - (a) Keep `Option` and leave the fallbacks. Rejected: the copies drift again.
   - (b) Accessor methods in `ess-ui` that apply the default. Rejected: that is one copy in
     `ess-ui` instead of the schema.
   - (c) Chosen: plain fields where the fill is unconditional.
