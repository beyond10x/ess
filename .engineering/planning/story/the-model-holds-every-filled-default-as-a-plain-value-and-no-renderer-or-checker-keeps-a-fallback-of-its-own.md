## Need

After the default units, the loader writes every default into the tree, but the model still types
most of them as `Option<T>`. Each renderer still carries the fallback it used before, now dead code.
The table of `g03-loader-fills-defaults` lists them. Among them:

- `collection.style`: `crates/ui/ess-ui-react/templates/runtime/composites/collection.tsx.tmpl:116`,
  `:541`; `crates/ui/ess-ui-tui/src/view.rs:1414-1415`; `crates/ui/ess-ui-test/src/parity.rs:84-85`.
- `Document.actor`: `crates/ui/ess-ui-react/src/emit.rs:3322-3325`.
- `when_paged_away`: `crates/ui/ess-ui-tui/src/app.rs:2511-2516`.
- `rich_text.syntax`: `rich_text.tsx.tmpl:21`, `view.rs:1221`.
- `confirm.confirm_label`: `confirm.tsx.tmpl:131`, `view.rs:2417-2420`.

A fallback that stays will one day disagree with a changed schema default again, which is how the
eleven disagreements arose. The earlier draft's acceptance said: "`Document` holds the same values,
and no renderer keeps a fallback of its own."

## Outcome

- Every model field the loader always fills is a plain `T`, not `Option<T>`. The conditional ones
  (`Field.unit`, `Field.scale`, `metric.unit`, `metric.scale`) and the model-filled `form.fields`
  stay optional.
- Every renderer, emitter, template and checker reads the field directly, and its own fallback is
  deleted. In the React templates a `?? <default>` on a prop the emitter now always passes is
  deleted too.
- A test fails when a schema default maps to an `Option` model field that is not on the named list
  of conditional or model-filled keys.
- No behaviour changes and no generated byte changes, apart from the deleted template fallbacks.

## Acceptance

1. `every_filled_default_is_a_plain_field` (in `crates/ui/ess-ui/tests/defaults.rs`). Red today.
   - The test lists each `default:` of the embedded schema with the model field it fills.
   - It fails for an `Option` field outside the named list.
   - A compile-time check is used where possible: a function that takes each field by value
     without `unwrap`.
2. `cargo test` passes for `ess-ui`, `ess-ui-tui`, `ess-ui-react`, `ess-ui-test`, `ess-ui-check`
   and `ess-ui-docs`, with no test expectation changed. Every `ess-ui-test/1` corpus report is the
   same.
3. `git grep -n "unwrap_or\|map_or\|?? " -- crates/ui` finds no fallback for a key on the filled
   list. The test names each remaining hit that belongs to another key, with the reason.
4. The `ess-ui-resolved/1` golden files do not move.
5. Each test is timed. None may run over 60 s, and each crate's test step stays within 120 s.

Also: `CHANGELOG.md`, under Changed, notes the Rust API change: the model fields are no longer
`Option`. That breaks downstream Rust code that matched on them, so it ships in a minor release.

## Fit review

Read at tree `bcfc51555`. The request came from a downstream application on 2026-11-24, report
item 3. This is the cleanup the owner's order implies: one table, in the schema, applied once.

1. **Need.** No second copy of a default exists anywhere.
2. **Class.** It is maintenance of a *gap* fix: it keeps the defects fixed in the default units
   from coming back.
3. **Already expressible?** Not applicable.
4. **Fit.** There is no authored surface and no format.
5. **Second adopter.** Every future change of a schema default, which is then one edit.
6. **Cost.**
   - A wide mechanical diff across six crates, which conflicts with every open story that edits
     the same fields. That is why it lands last.
   - A Rust API break for downstream users of `ess-ui`'s model.
7. **Considered.**
   - (a) Keep `Option` and leave the fallbacks. Rejected: the copies drift again.
   - (b) Accessor methods in `ess-ui` that apply the default. Rejected: that is one copy in
     `ess-ui` instead of the schema.
   - (c) Chosen: plain fields.
