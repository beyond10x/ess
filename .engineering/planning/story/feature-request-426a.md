## Outcome
Resolve beyond10x/ess#426 (part a): a case-record domain derived from a Canon protocol is generated by its producer, not imported by ESS. A design note says so and states the idioms a generator uses.

## Origin
beyond10x/ess#426, filed 2026-10-05; a downstream factory's spike hand-derived one case-record domain from an engineering protocol on ess 0.52.0. Full fit review in story 426.

## Fit review
1. Need: a generator author needs to know which ESS shapes a generated case record must use, and that ESS will not read `protocol/1` itself. Proposed by the requester: an ESS import adapter (refused in 426, Q4). Minimal reproduction: `<fit-review scratch>/probe-426/b` validates; `a`, `c` and `f` are refused.
2. Class: convenience. Every construct the spike needs is expressible today (issue body: `valid`, `compiled`; probe `b`: `probe v1 — 1 file(s), valid`).
3. Existing idiom: quoted variants `["True", "False", Unknown]` validate (probe `b`); structured `all:` validates and compact `a and b` is refused with "use structured any/all/not" (probe `c`; docs/design/refused-misparsed-predicate-disjunctions.md:15-18); a refusal default beside a guarded `when_subject` success validates at four claims (probe `h`), and a guarded pair validates at two and three claims (probes `d`, `i`) and is refused at four (probe `f`; cap at finite.rs:10).
4. Fit: a design note plus one regression test, with no authored surface. The existing imports emit IR and envelopes, not authored source (crates/generate/ess-openapi/src/accounting.rs:10; main.rs:1061-1092). The note says a producer that owns its format writes authored `ess/N` source and pins the reading release with `ess-inputs.yaml` `requires:`. It names `ess-protospec/1` as unrelated, so "protocol" keeps one meaning in ESS (CHANGELOG.md 0.53.0).
5. Second adopter: an approval-workflow engine emitting one domain per workflow definition reads the same note.
6. Cost: one page, one test file, one guide link. No format bump (ess/22 unchanged), no diagnostic, no diff class.
7. Alternatives: change nothing, so every generator author rediscovers the three pitfalls (the issue lists them as found by trial); ship an ESS adapter (refused, 426 Q4); chosen: note plus test.

## Decisions
Decline the ESS adapter, with the idiom. Write `docs/design/generated-case-record-domains.md` with four sections:
- (a) `## A producer emits authored source`: ESS imports read sources ESS does not own, into IR. A producer owning a format, Canon included, emits authored source and gates it with validate, compile and synthesize, as Canon's `ess/` gate does (canon AGENTS.md "ESS").
- (b) `## Three idioms a generator uses`: quote every scalar, structured `all/any/not`, the refusal as the default branch. Past 64 joint assignments a default is required.
- (c) `## The meaning stays in Canon`: the meaning of a protocol stays in Canon's conformance (Atlas ADR 0067, 0076). The derivation profile is Canon's (`canon-case-record/1`), not ESS's.
- (d) `## Names`: "case-record domain" is ESS's term, and `ess specify protocol` is unrelated.

The story body is the decline record. No format bump.

## Acceptance
- quoted_true_false_variants_validate: an enum declaring `"True"`, `"False"` and `Unknown` validates, and a guard `x == "True"` selects it.
- structured_all_conjunction_validates: `when_subject: {predicate: {all: [a == "Holds", b == "Holds"]}}` validates.
- compact_and_is_refused_naming_structured_form: `a == "Holds" and b == "Holds"` is refused with "use structured any/all/not".
- refusal_default_beside_guarded_success_validates: a guarded success over four three-valued fields beside an unguarded refusal validates.
- guarded_pair_within_cap_validates: a guarded success and its guarded negation over three three-valued fields (27 assignments) validate.
- guarded_pair_past_cap_is_refused_non_exhaustive: the same pair over four fields (81 assignments) is refused `non_exhaustive_branches` at `<command>.outcomes`.
- generated_case_record_note_states_the_boundary: `docs/design/generated-case-record-domains.md` exists and carries the four headings above. Section (a) states "`protocol/1`", "no ESS import adapter" and "validate, compile and synthesize". Section (b) states "quote every scalar", "`all`/`any`/`not`", "default branch" and "64 joint assignments". Section (c) states "ADR 0067", "ADR 0076" and "`canon-case-record/1`". Section (d) states "case-record domain" and "`ess specify protocol`". The case reads the note and fails naming the missing heading or phrase. It splits sections by heading the way `crates/edge/ess-xtask/tests/d2_constraint_home_adversary.rs:116-123` does.
- guards_guide_links_the_generated_case_record_note: the section `## Guard an outcome by the subject's stored fields` of `website/docs/guides/specify/guards-and-predicates.md` holds a link whose target ends in `docs/design/generated-case-record-domains.md`. Same test file; `task site-build` is not the check, because it does not resolve a design-note link.
