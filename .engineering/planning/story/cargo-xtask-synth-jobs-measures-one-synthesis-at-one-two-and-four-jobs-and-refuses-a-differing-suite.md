## Outcome

`cargo xtask synth-jobs` runs `ess verify conform synthesize --target ir` once each at
`ESS_SYNTH_JOBS` 1, 2 and 4 on one model. By default the model is generated by the xtask; with
`--path` it is any specification. The command:

- prints one row per job count: wall time, user CPU time, system CPU time, peak resident memory,
  the suite's scenario count and SHA-256, and the speed-up against one job;
- exits 1, naming the two counts, when the suite bytes differ between any two of them.

A task `synth-jobs-profile` builds the release binary and runs it. The design page
`docs/design/parallel-caller-readings.md` gets a `## Measured` section with the table from this
host. The default stays 1; the table is what the operator reads before any default changes.

This unit does not judge the parent's "N = 4 takes at most 45 % of N = 1". The coordinator
judges that on the largest known downstream specification, with the wave's release build and
this command's `--path`, and records it in the parent (routing decision X11).

## Why

- Parent: `story:the-caller-readings-of-a-synthesis-run-on-several-threads-and-write-the-suite-a-single-thread-writes`.
  Its rule: peak memory and CPU are measured at 2 and 4 threads before any default changes. The
  tool is a committed `cargo xtask` subcommand on a generated model, because the downstream
  specification is private and no unit can read it. The parent records that decision (X11).
- Consumer gap: one synthesis of the largest known downstream specification takes 279 s on one
  core. The parent's 3.5x is an estimate. Unit `p3`'s lanes put each uniform model's readings on
  one thread, so the expected gain is lower (inferred about 2.2x; see `p3` D3). This unit
  replaces the estimate by a number.
- The model is generated, not committed:
  - a committed YAML model under `crates/verify/**/fixtures` or `models/` would be walked by
    `synthesis_suite_bytes_table.rs` (it reads every ESS YAML of the repository) and add a row
    and test time there;
  - a generator that takes a size reaches a run of 20-120 s, which is what a measurement needs.

## Tests first

- Bounds: no test over 60 s, a test step within 120 s. Time each new test and name any over 5 s.
- The tests are unit tests in `crates/edge/ess-xtask/src/synth_jobs.rs` (`#[cfg(test)] mod
  tests`). There is no new test binary, and no test builds with cargo or starts `ess`
  (`tests/no_test_builds.rs`).

1. `the_generated_model_compiles_and_reads_the_caller_in_its_marks`: `model(2, 1)` is parsed,
   assembled and compiled the way `caller_readings_made_once_work.rs` 148-153 does. It has
   commands `Open`, `Mark1`, `Mark2` and `Close`, and the text of `Mark1` (and not of `Mark2`)
   holds `owner_id != caller.owner_id`. Red today: the module does not exist.
2. `the_generated_model_grows_with_its_flags`: `model(24, 12)` compiles and has 26 commands.
   Keep it under 5 s; it compiles and does not synthesize.
3. `a_status_line_gives_the_peak_resident_memory`: `peak_kib("Name:\tess\nVmHWM:\t  123456 kB\n")`
   is `Some(123456)`, and a text without `VmHWM` is `None`.
4. `a_stat_line_gives_the_childrens_cpu_ticks`: `children_ticks` of a `/proc/self/stat` line
   whose command name holds a space and a parenthesis, `"12 (a b) c) S 1 2 …"`, reads `cutime`
   and `cstime` (fields 16 and 17 counted from 1). The parser splits after the last `)`.
5. `differing_suites_are_refused_with_both_counts`: `compare(&[(1, digest_a, 7), (2, digest_a, 7),
   (4, digest_b, 7)])` is `Err` with text naming `1` and `4`; a differing scenario count with
   equal digests is `Err` too; three equal rows are `Ok`.

## Steps

1. Record `BASE=$(git rev-parse HEAD)`. Write tests 1-5 and record the red lines.
2. Write `crates/edge/ess-xtask/src/synth_jobs.rs` in Rust (no Python, no shell checker):
   - `pub fn model(flags: usize, reading: usize) -> String`: the card model of
     `caller_readings_made_once_work.rs` with `flags` flags. Make two changes:
     - `Mark1..=Mark<reading>` also get an outcome `not-owner` before `marked`, with
       `when_subject: predicate: owner_id != caller.owner_id` and error `NotOwner`;
     - the actor always has the `owner_id` attribute.

     With that, those marks are focused readings off the uniform models: they are the pool work
     of `p3`. The other marks are lane work.
   - `pub fn run(root, args) -> Result<String>`. `args`:
     - `--flags` (24) and `--reading` (12);
     - `--path` and `--scenarios`, passed to `ess` as they are; with `--path` no model is
       generated;
     - `--ess` (default `target/release/ess`);
     - `--jobs` (a list, default `1,2,4`).

     Steps of `run`:
     1. Write the model to `target/synth-jobs/board.yaml` under the workspace root, never `/tmp`.
     2. For each count, run the binary with `verify conform synthesize --path <model> --target ir
        --out target/synth-jobs/suite-<n>.json --compact` and `ESS_SYNTH_JOBS=<n>` in its
        environment.

        Do not use `--jobs`: unit `p4` adds it in parallel. The variable is `p3`'s.
     3. Measure each child:
        - wall time from `std::time::Instant` around `spawn` and `wait`;
        - CPU time as the change in `cutime` and `cstime` of `/proc/self/stat` across the
          child's `wait`, in ticks of 1/100 s (`USER_HZ` on Linux x86_64);
        - peak resident memory as the largest `VmHWM` of `/proc/<pid>/status`, read every 20 ms
          while the child runs. It is a lower bound by at most the last 20 ms; say so in the
          output's last line.
     4. Hash each suite file with `sha2::Sha256`, and read its scenario count with `serde_json`
        (the number of entries of the suite document's `scenarios`). Then call `compare`, which
        refuses a differing digest or count.
     5. Print a Markdown table (`| jobs | wall s | user s | sys s | peak MiB | speed-up |
        scenarios | suite sha256 |`). Then one line naming the model and its flags, reading and
        command count, the host's core count (`std::thread::available_parallelism`), and the
        1-minute load read from `/proc/loadavg` before the first run and after the last.
   - On a non-Linux host: a clear refusal, "synth-jobs reads /proc and runs on Linux only".
3. Register `mod synth_jobs;` and `Command::SynthJobs { .. }` in `main.rs`, dispatched like
   `SiteData`.
4. Add the task to `Taskfile.yml` at the end of the `tasks:` map:

   ```yaml
   synth-jobs-profile:
     desc: Measure one synthesis at 1, 2 and 4 jobs (wall, CPU, peak memory); refuses differing suites.
     cmds:
       - SLOT_TIMEOUT=30m cargo build --release --locked -p ess-cli
       - cargo build --locked -p ess-xtask
       - target/debug/ess-xtask synth-jobs {{.CLI_ARGS}}
   ```

   - The two builds take a pool slot through the shim.
   - The measurement runs outside the pool: it measures, so it holds no slot (the organization AGENTS.md,
     "Scripts that do not build stay off slot"). Run the task without the `slot` prefix.
   - No `RUSTC_WRAPPER`, `SCCACHE_*` or `-j` in it.
5. Tune the size. Run `task synth-jobs-profile` (no `slot` prefix) only at a 1-minute load of 60
   or less (`cut -d' ' -f1 /proc/loadavg`), on a warm release build. Raise `--flags` and
   `--reading` until the one-job row's wall time lies between 20 and 120 s; record the values
   and make them the defaults. Each run of the three counts must end within 10 minutes. If one
   count alone runs over 5 minutes, lower the size. A run started above load 60 is repeated,
   not reported.
6. Replace the `## Measured` placeholder of the design page with:
   - the table;
   - the date, the commit, the host's core count and its load average at the start
     (`/proc/loadavg`), and the command;
   - one sentence on the speed-up at 2 and at 4 jobs against the parent's estimate of 3.5x;
   - one sentence on peak memory at 4 jobs against one job.

   If the operator runs the command on the largest known downstream specification, its row goes
   into the report to the operator only, never into the page: the page names no private model.
7. Run the gate.
8. One commit, message file via the Write tool, `git commit -F <file>`:
   `feat(xtask): synth-jobs measures a synthesis at 1, 2 and 4 jobs`. The body holds the table.

## Gate

- Each build or test command is one pool job; `cargo` is the shim.
- Bounds: 60 s per test, 120 s per test step. A pool job ends after 10 minutes unless it names
  its time, 30 minutes at most (`SLOT_TIMEOUT=30m`).
- No Python, no `/tmp`, no `RUSTC_WRAPPER`, `SCCACHE_*` or `-j`.

```console
slot task fmt-check
SLOT_TIMEOUT=30m CARGO_PROFILE_DEV_DEBUG=false CARGO_INCREMENTAL=0 cargo clippy -p ess-xtask --all-targets --locked -- -D warnings
SLOT_TIMEOUT=30m slot task test-xtask
SLOT_TIMEOUT=30m slot task ci-lint
task synth-jobs-profile
```

- `task synth-jobs-profile` runs without the `slot` prefix: it builds through the shim and
  measures outside the pool.
- `test-xtask` runs `scratch_leaks`, `host_paths*` and `layout`, which refuse host paths and
  `/tmp` in committed files; the new module must pass them.

## Acceptance

1. Tests 1-5 pass, with their times reported.
2. Decided by counts and identical suites: `task synth-jobs-profile` exits 0 and prints exactly
   three rows (jobs 1, 2, 4). All three have one SHA-256 and one scenario count, and the count is
   above 0. The model line names `flags + 2` commands.
3. Stated, not judged: the one-job row's wall time lies between 20 and 120 s at a 1-minute load
   of 60 or less, warm release build. The printed load line shows the load at both ends.
4. The refusal of differing suites is covered by test 5. A real run cannot be forced to differ
   from outside, and the report says so.
5. The design page's `## Measured` holds the table, the commit, the host's core count and the
   load, and names no private model.
6. `git diff $BASE -- Cargo.lock '**/Cargo.toml'` is empty.
7. `git grep -n -i python -- crates/edge/ess-xtask/src/synth_jobs.rs Taskfile.yml` shows no new
   line.

## Decisions

- D1. The xtask, not a test: a measurement is not a test, takes 1-6 minutes, and must not run in
  the test step (60 s per test, 120 s per step).
- D2. The job count is set by `ESS_SYNTH_JOBS`, not `--jobs`, so this unit depends on `p3` only
  and runs beside `p4`.
- D3. Peak memory comes from polling `VmHWM`, with no `libc` dependency for `getrusage` (none
  exists in `ess-xtask`, `Cargo.toml` 10-29). The 20 ms poll gives a lower bound; it is stated in
  the output.
- D4. Release build: the adopter runs the release binary, and a debug synthesis of this size runs
  far longer than the bounds allow.
