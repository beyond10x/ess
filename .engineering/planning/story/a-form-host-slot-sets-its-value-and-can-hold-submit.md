## Need

A host slot that stands in for a form field or for a tab's `form` receives only
`{adapter, path, page, scope}` in the generated React project. The component can read the
form's draft through `scope`, but it cannot set the field's value, and it cannot hold the form
back while its own input is incomplete. The adopter's form hosts write the draft: flow-step-editor,
option-form, widget-filter-form, weekly-schedule, cron-editor, provider-form, record-list. Together
with the multi-view gap this blocks about 45 of their 84 host entries
(a downstream report, 2026-11-09).

The terminal already keeps keys at a form field slot from editing anything, so the form never sends
a value the host's input did not set (0.92.0). The React runtime needs the same rule, with the
host able to set the value.

## Acceptance

- A host slot at a form field, or at a tab's `form`, receives a typed form-value prop. With it the
  component reads the form's draft, sets the value at its own path (or, for a tab's `form`, the
  values of the fields it stands in for), and marks the form blocked so submit is refused until it
  clears the mark.
- The form never sends a value at a slot's path that the host did not set. A slot that set
  nothing sends nothing there.
- A slot at a page, section, overlay or nested node receives no form-value prop. Its props and the
  generated bytes for documents without form slots are unchanged.
- The value the component sets is typed by the field's type in the specification, so a wrongly
  typed value fails `tsc`.

## Scope

- inferred: `crates/ui/ess-ui-react/src/emit.rs` and the hosts and form runtime templates (the
  prop, submit blocking), `crates/ui/ess-ui-react/tests/host_slots.rs`, design:ui-host-slots (a
  section on form slots); the terminal behaviour is the reference.
