## Need

Found by the adversary pass on
`story:a-generated-rust-view-query-applies-its-parameters-and-orders` (turn 3). The defect is older
than that story and outside its acceptance. A view filter that compares an optional stored field
is generated for Rust and Go. This holds for a comparison with a parameter (`note == param.note`)
and with a literal (`note == "x"`; the existing `LongTasks`, `hours >= 5` over
`Optional<Integer>`, is the same shape). The generated query answers the read and drops the rows
that lack the field. The interpreted target refuses the whole read instead
(`crates/verify/ess-conformance/src/interpret/views.rs:214`). The decision is made at
`crates/generate/ess-synth/src/determined.rs:965`.

The two answers differ, so a conformance suite cannot check this read, and a user gets an answer
where the reference has none. The story above owes an optional parameter for exactly this reason
(`determined.rs:948`). An optional stored field is the same case, but it stays generated.

```text
gap.demo.NoteIsX {}: interpreted cannot expose interpreted view: the model does not determine a complete typed view observation | rust ["a1", "a4"]
```

The probe is the differential case
`crates/generate/ess-synth/tests/generated_view_queries.rs::adversary_rust_typed_parameters_and_orders_answer_as_the_interpreted_target`
(and its Go twin). Its `ADVERSARY_VIEWS` still declare `NoteIs` and `NoteIsX`, but its reads leave
them out.

## Acceptance

- A generated Rust and Go query whose filter compares an optional stored field either answers as
  the interpreted target does or stays owed, with a named reason. Both targets decide alike.
- The interpreted target and the generated servers agree on `NoteIs` and `NoteIsX`, once those reads
  are added back to `ADVERSARY_READS` in the differential cases above.
- A view whose filter reads no optional field keeps its generated bytes.
