## Outcome

The design page and the generated Go server say the same thing about a body whose `Content-Length`
exceeds the fixed 1 MiB bound: either the Go server refuses it from the request head as the Rust
server does, or the page says the Go server reads up to the bound first. Today the page's rule 1a
says the first and one Go path does the second.

## Need

**Reading.** Verified at the wave head `b2cdf564b` (`origin/integration/wave-2026-11-23`); the page
and the capped Go path are not on `main` in this form yet.

- `docs/design/http-presentation-binding.md:698-703`, rule 1a of "Precedence": "The request head
  decides, before the body is read and before the 404, the 405 and the grant check, as the fixed
  bound does today. That holds for a request whose `Content-Length` exceeds the bound". The
  "Request size" bullet (`:741-747`) then says per target how an unannounced length (chunked) goes:
  Rust answers `411`, Go reads up to the bound plus one byte.
- Rust: `crates/generate/ess-synth/src/rust/http.rs:2057-2060` answers `413` from the parsed
  `Content-Length` before it allocates or reads any body byte.
- Go, a package where some served component caps a request: the rewritten `readBody`
  (`crates/generate/ess-synth/src/go/http/bound.rs:82-83`) tests `request.ContentLength >
  reading.limit` first and returns the refusal without reading, as rule 1a says.
- Go, a package where no component caps (the fixed bound only): `readBody`
  (`crates/generate/ess-synth/src/go/http.rs:2863-2879`) has no such test. It reads
  `io.LimitReader(request.Body, maxBody+1)` (`:2869`) and refuses afterwards (`:2874-2875`). A
  request announcing 10 MiB therefore has 1 MiB + 1 byte read before the `413`, where the Rust server
  reads none. Status, headers and the refusal's JSON member agree; what differs is the bytes read
  and the refusal's wording ("the body is longer than N bytes, which is all this surface reads"
  against "the body is {length} bytes and this surface reads at most N").
- The wave close's security review recorded the chunked half of this as drift (page said both
  servers read to the bound plus one); the head's page already states it per target. The
  announced-length half is the one left, and the notes of the close do not settle which side moves.

## Acceptance

After decision D1, a test in `crates/generate/ess-synth/tests/http_binding/` sends a request announcing
`Content-Length` of twice the fixed bound and no body bytes to the generated Go server of a
binding that caps no route and to the generated Rust server, and the two answers agree with the
page: under A both answer `413` without the request blocking on the missing bytes; under B the page
says the Go server reads first, and the same test pins that sentence by reading the bytes the
server consumed.

## Decisions

- **D1 (open): which side changes.** A (default): the Go fixed `readBody` tests `ContentLength`
  first, as the capped one does and as the Rust server does; the page stays. The generated Go
  bytes of every package without a cap move (any committed generated Go tree of such a package, whose
  pins are re-stamped), and a changelog line says so. B: the page's rule 1a is
  narrowed to the Rust server and the capped Go path, and "as the fixed bound does today" is
  dropped for Go; no generated byte moves. A is the default because the capped path already
  holds the rule, so one Go server would otherwise hold two behaviours for one rule.
- **First step.** D1; nothing is implemented before it is decided.

## Scope

- `docs/design/http-presentation-binding.md` (rule 1a, "Request size")
- `crates/generate/ess-synth/src/go/http.rs` (`readBody` of the fixed bound), under A
- `crates/generate/ess-synth/src/go/http/bound.rs` (`capped_read_body`, the rewrite that must still find its base), under A
- `crates/generate/ess-synth/tests/http_binding/` (the new case)
