- `ess generate ui --target react|tui --http <binding>`, and `ess ui run --http <binding>`, take each
  view's and command's path, method and parameters from the `ess-http/1` binding. The generated
  binding table carries the method, and both runtimes use it.

  command and the binding.

## Problem

beyond10x/ess#713, a gap reported 2026-10-30 by a downstream session on ESS 0.77.0 that works around it
with a hand-written path shim. Re-checked with `ess 0.77.0` on a toy spec with an `ess-http/1` binding.

`ess generate ui` (`--target react` and `--target tui`) and `ess ui run` take no binding.
`binding.ts` and the TUI's `binding.rs` call the default served surface: `GET
/items/views/AllItems`, `POST /items/commands/add-item`. The table carries no method, and the React
runtime hard-codes GET for views and POST for commands.

`ess generate synthesize --target rust --layout crate --http <binding>` serves the binding's routes
(`GET /items`, `POST /items`). All four UI calls answer 404 from that server, and neither generator
warns. A UI and a service generated from one specification do not meet.
