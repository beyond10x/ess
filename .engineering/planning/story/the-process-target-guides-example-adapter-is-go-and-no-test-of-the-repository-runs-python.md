## Outcome

The complete adapter on the process-target guide page is a Go program on the standard library, and
the test that runs it builds it once and runs the guide's command against it. No page, test, task,
CI step or committed file of the repository runs, or tells a test to run, Python.

## Need

The organization rule "No Python for permanent tools" (`~/beyond10x/AGENTS.md`) bars Python in
anything that stays in a repository, test helpers included, and makes existing Python a defect that
gets a story. `ess/AGENTS.md` § Boundaries already says "Anything executable is Rust. Do not add
Python or shell checkers."

`git ls-files '*.py'` lists no file at `16f2fc88c2`. The one place a test runs Python is a code
block on a page:

- `website/docs/guides/verify/target-process.md:179` holds an 84-line Python 3 adapter (lines 179-264) in a block
  titled `adapter/adapter.py`. The page also names `python3` in its command (line 27), in the
  sentence on `PATH` lookup (line 42) and in the number advice (line 153, `parse_float=
  decimal.Decimal`).
- `crates/edge/ess-cli/tests/process_target_guide.rs` takes that block out of the page byte for
  byte (`ADAPTER`, line 24), writes it as `adapter/adapter.py` (line 127) and runs
  `-- python3 adapter.py` (lines 180-181). Two tests, `the_guides_python_adapter_passes_every_scenario_of_its_specification`
  (line 210) and `the_guides_adapter_with_one_wrong_outcome_fails_that_scenario` (line 238, which
  replaces `took("rejected"` with `took("added"`), return early with a printed skip when `python3`
  is not on `PATH` (`python_skipped`, line 78). The file's header (lines 11-13) argues that this is
  "documentation under test, not a checker": the rule above does not make that exception.

Every other mention of Python is prose or an advice string, none run by a test:

- `website/docs/guides/verify/runners.md:152` ("a complete adapter in Python 3"),
  `website/blog/2026-11-21-1200-conformance-in-any-language.md:49` and `CHANGELOG.md:150` (history,
  not edited).
- `docs/design/conformance-target-process.md`: § "A minimal adapter in Python 3" (line 843), the
  number advice (line 379), the test names (line 1039) and settled question 3 (line 1165). Line
  1124 discusses `--target python` as a rejected alternative and stays.
- Three copies of the advice `python3 -m http.server`, printed to a reader of generated web
  output: `crates/generate/ess-synth/src/web/mod.rs:719`,
  `crates/verify/ess-conformance/src/web.rs:293` and, as committed output of the first,
  `generated/web/billing/README.md:44`. No test runs the command.

The toolchains of the test step decide the language. `ci.yml` installs Go 1.25.10 (line 538) and
Node 22 with `typescript`, `prettier` and `esbuild` in the job that runs the test shards (lines
555-572); Rust is the repository's own. `tutorial_page.rs` already runs `go` steps and skips with
a printed reason when it is missing (`go_skipped`, line 368), and `ess-conformance` and `ess-synth`
build Go servers in tests. A Go adapter is one file on the standard library: `encoding/json`
reads and writes numbers as exact tokens (`Decoder.UseNumber`, `json.Number`), which is what the
page's number advice asks for, and it takes no dependency. A Rust adapter needs a JSON parser the
page cannot assume (the guide's reader has no crate), and a TypeScript one needs `tsc` and `node`
per run.

## Fit review

A defect against an organization rule, not an adopter request. The need is one page block, one test
file and two pages of prose; no format, no generated byte and no `ess/N` is involved. The guide
stays what its design page says it is (`docs/design/conformance-target-process.md` § "A minimal
adapter"): a complete adapter in a language other than the one `ess` is written in, executed by a
test so the page cannot rot. Only the language changes.

## Design

- The page's adapter becomes `adapter/adapter.go`, `package main`, standard library only
  (`bufio`, `encoding/json`, `fmt`, `os`). It keeps the behaviour of the Python one line for line:
  the same `tasks` specification, `handshake`, `begin_scenario`, `end_scenario`,
  `execute_command`, `query_view`, `observe_events`, `unsupported` for what it does not serve,
  consistency token from every command, identities from a counter. Numbers read with
  `UseNumber`, so the page's advice becomes "Go: `Decoder.UseNumber`" in place of the `decimal`
  line.
- The page's run section builds first, then runs: `go build -o adapter adapter.go` in `adapter/`,
  and the command ends `-- ./adapter` (the sentence at line 42 already explains `./adapter`
  against `--target-dir`). The sample output block names the implementation `tasks-go 1.0.0`.
- `process_target_guide.rs` takes the block titled `adapter/adapter.go`, builds it with `go build`
  and runs the guide's command. It builds each of its two sources once per run, not once per test:
  the binary is a cache entry on disk under `target/`, named by the sha256 of its source (the form
  `AGENTS.md` of the organization accepts), built under a file lock so the two test processes of
  cargo-nextest do not both build it. The wrong-outcome test builds the page's source with
  `took("rejected"` changed, as today, and that binary is a second entry. `go_skipped` copies the
  pattern of `tutorial_page.rs`: a printed skip where `go` is not on `PATH`.
- `python_skipped`, the `.py` names and the file header's argument go. The header says the Go is
  documentation under test.
- The prose that names the Python adapter changes to name the Go one: `runners.md:152`, the
  design page's § "A minimal adapter" and settled question 3, the test names (renamed, and
  the design page's line 1039 with them). The blog post
  and `CHANGELOG.md` are history and keep their words; the next `CHANGELOG.md` entry says the
  guide's adapter is Go.
- The three `python3 -m http.server` advice strings are decision A.

## Acceptance

- `git grep -n -i 'python' -- crates Taskfile.yml .github website/docs docs/design` prints only
  lines that name Python as a thing the repository does not use: the rejected `--target python`
  alternative at `docs/design/conformance-target-process.md:1124` and any line the decision A
  keeps. `git ls-files '*.py'` prints nothing.
- `go vet` and `gofmt -l` accept the page's block (the test fails when `gofmt -l` prints the file),
  and the test passes: all 6 scenarios of the `tasks` suite pass under `--strict`, exit 0.
- The wrong-outcome test still exits 1 with exactly `tasks.list.AddTask/outcome/rejected` failed.
- Each of the two tests runs in 60 s or less and the pair in 20 s or less on a cold `GOCACHE`
  (time of `cargo test -p ess-cli --test process_target_guide` named in the pull request); the
  second run in the same `target/` builds nothing (the cache entry is hit), shown by the test's
  own count of builds, which is 0.
- With `go` not on `PATH` both tests print their skip and pass, as `tutorial_page.rs` does; CI's
  test job has Go 1.25.10, so there they run; a new case of `ci_lanes.rs` fails when that job installs no Go (no case pins it today).
- `task test-xtask` passes: pages and design are read by it, and a changed page moves nothing it
  pins.

## Decisions

A. The three `python3 -m http.server` advice strings in generated web output, which no test runs
   and which tell a reader to use a tool already on their machine.
   - Keep them (recommended: the rule bars Python the repository keeps and runs; an advice line
     for the reader's shell is neither, and changing them moves the committed generated tree
     `generated/web/billing` and every byte pin that compares it).
   - Replace them with a Go or Node one-liner that serves the directory (moves those bytes and
     the three places in one change; a reader without that tool is worse off).

B. The adapter's language, if Go is not accepted: TypeScript (`tsc` and `node` are in the CI test
   job; two process starts per build) or Rust (the page's reader has no JSON crate; the adapter
   would hand-roll a parser). Recommended: Go, for the reasons in Need.
