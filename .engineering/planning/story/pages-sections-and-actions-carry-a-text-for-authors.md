## Need

A UI document is read by people and by tools that generate from it. A page, a section and an action
have no place for a sentence that says what they are for. A widget has `summary` and `doc`, and a
field has `note` (`website/docs/reference/ess-ui.md`), so the format already has the idea and
spells it two ways.

Evidence: a consumer's UI document (2026-11-13, ess 0.94.0), a smaller item of its collected report.

Base document for the reproductions (ess 0.94.0, brand-free): one entity `Request` with a
`Pending` state, a command `ApproveRequest {id}`, a view `PendingRequests` (fields `id`, `title`,
`state`), a page `requests.inbox` whose section `list` is a `collection` over that view, and a page
`requests.detail` with a param `id`. `ess ui check --model` on the base: `0 error(s), 0 warning(s)`.

Reproduction, `description:` on each of the three:

```
error document_loads pages/requests.inbox: unknown field `description`, expected one of `kind`, `shell`, `title`, `nav`, `params`, `aliases`, `switch_to`, `visible`, `actor`, `layout`, `state`, `header`, `sections`, `overlays`, `profile`, `source`, `unmapped`
error document_loads pages/requests.inbox/sections/list: `collection`: unknown field `description`, expected one of `reads`, `columns`, ...
error document_loads pages/requests.inbox/sections/list/row_actions/approve: unknown field `description`, expected one of `name`, `does`, `bind`, ...
```

## What a design has to settle

- One key name for an author's text on every node that takes one (`doc`, as a widget has, or
  `note`, as a field has), not a third spelling.
- Whether a renderer ever shows it (a tooltip, generated documentation from `ess ui docs`) or
  whether it is for authors and tools only, and that it never changes what a renderer draws.

## Acceptance (sketch, to be fixed by the fit review)

- The three nodes accept the chosen key, `ess ui load` reports it, and no generated byte of the
  React project or the terminal changes for a document that adds it.
