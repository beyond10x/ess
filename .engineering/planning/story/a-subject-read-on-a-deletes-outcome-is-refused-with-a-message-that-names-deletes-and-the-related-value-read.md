# d796: a subject read on a deleting outcome is refused naming `deletes:`

Size: S (about 60 changed lines: 25 source, 35 test).
Fixed suite bytes of committed models: none move (validation text only; no IR, suite or generated byte changes).
Patch-release candidate: yes (no committed byte, no diagnostic code changes; ESS-COMMAND-004 and `conflicting_declaration` stay).

## Need

beyond10x/ess#796. Validation refuses `{subject: <field>}` in the event payload of an outcome that
deletes the row, and the refusal says the outcome is a `creates:` outcome with no row before it.
Its hint ("read the value from the command's input instead") does not apply: the stored field is
not in the input. The author is told a wrong fact about their model and given no way forward.

## Reproduction

Reproduced on 0.98.0. Model `repro/796/` (`system.yaml` at `format: ess/37`, `domains/racks.yaml`):
entity `depot.racks.Shelf {shelf_id: Uuid, label: String}`; `RemoveShelf` with
`unknown-shelf` (`unknown_instance: true`) and `removed` (`deletes: depot.racks.Shelf`,
`instance: shelf_id`, payload `ShelfRemoved: {shelf_id: input.shelf_id, label: {subject: label}}`).

```console
$ ess specify validate --path .
  - error[ESS-COMMAND-004]: `{subject: …}` reads `depot.racks.Shelf` as it was before outcome `removed`, and a `creates:` outcome has no row before it
  help: read the value from the command's input instead
exit 1
```

Measured beside it (same binary), each a model of its own run with `--path repro/796-via` and
`--path repro/796-where`: `label: {related: {via: input.shelf_id, field: label}}` and
`label: {related: {entity: depot.racks.Shelf, where: shelf_id == input.shelf_id, field: label}}`
both validate, and the first synthesizes 3 scenarios that pass on the interpreted target; the
suite checks only the shape of `label` (`expect_event_values` with `shape.label`), not its value.
(`repro/796-preserves/`: a `preserves:` outcome cannot carry a payload at all, so it never reaches
this refusal.)

## Outcome

The refusal of a read of the row before the outcome names the outcome's own effect. On a
`deletes:` outcome it says the outcome deletes the row and that `{subject: …}` is not read there.
Its hint depends on the read:

- `{subject: <field>}` (and the other reads of the subject's own field) where the outcome's
  `instance:` names an input: `{related: {via: input.<that input>, field: <field>}}`, the read that
  validates today;
- the same where `instance:` names no input (a caller attribute, a minted identity): today's hint,
  "read the value from the command's input instead";
- `{related: {via: <subject field>, field: …}}`: "name the reference through an input field", since
  that form reads the row the stored reference names and the input must carry that reference.

On `creates:` the message and hint stay as they are. The same correction applies to the sibling
text in `related_via`'s hint (`value_expression.rs:841-861`; the function starts at 632), which
also says "a `creates:` branch" for every outcome that is not `moves:` or `updates:`.

## Acceptance

1. Red today: validating `repro/796/` reports ESS-COMMAND-004 (`conflicting_declaration`) at
   `command.depot.racks.RemoveShelf.outcomes.removed.payload.depot.racks.ShelfRemoved.label` whose
   message contains "`deletes:`" and does not contain "`creates:`".
2. The hint of that refusal names `{related: {via: input.shelf_id, field: label}}` (the outcome's
   `instance:` input and the field read), and does not say "read the value from the command's
   input instead". With `instance:` naming no input, the hint is "read the value from the
   command's input instead".
3. The `creates:` refusal is unchanged: the existing assertion in
   `crates/specify/ess-domain/tests/subject_state_source.rs` (message contains "`creates:`") and its
   hint "read the value from the command's input instead" still hold.
4. `{related: {via: <subject field>, field: …}}` in the payload of a `deletes:` outcome, which reaches
   the same function (`related_via`, from line 632; the call at 671), names `deletes:` too, not
   `creates:`, and its hint says to name the reference through an input field.
5. The message is chosen by a `match` over `Effect` with no wildcard arm, one arm per variant
   (`Creates`, `Moves`, `Updates`, `Preserves`, `Deletes`); `Preserves`, whose outcome carries no
   payload and so never reaches this refusal (`repro/796-preserves/`), maps to the existing text.
   A new effect fails to compile until it has a text.

## Fit review

1. Need: an author cannot tell from the refusal why a read of the deleted row is refused or what
   to write instead. The requester's two proposals, theirs: admit `{subject: …}` on `deletes:`, or
   name `deletes:` in the refusal.
2. Class: defect for the message (it states a false fact about the model:
   `value_expression.rs:1288` names `creates:` for every outcome whose effect is not `moves:` or
   `updates:`, line 78). The read itself is a convenience: it is expressible today (3).
3. Already expressible: `{related: {via: input.shelf_id, field: label}}` validates on the deleting
   outcome and its suite passes on the interpreted target (Reproduction). Caveat: the suite checks
   only the shape of `label`, so the figure is not value-checked; that is DF-D1's concern, not the
   message's.
4. Fit: no new key, no new code; the message follows the effect grid the outcome already has
   (`Effect` in `crates/specify/ess-domain/src/command.rs:962`).
5. A second adopter: any event that reports a removal (an archived record's title, a closed
   account's balance) meets the same message.
6. Cost: message and hint text; no format, no IR, no suite bytes.
7. Considered: change nothing (rejected: the message is false); admit the read (DF-D1 B, a meaning
   change that needs a format); fix the message (chosen).

## Decisions

- Decision: accept, redesigned. The message is fixed as reported; the requester's first option
  (admit the read) is DF-D1, default A: not in this unit.
- DF-D1 (see `DECISIONS.md`): A (default) keep the refusal, fix its text, point at the
  `{related: {via: …}}` read; B admit `{subject: …}` on `deletes:` from the next source format, in
  a story of its own with the suite checking the value; C admit it at every format.
