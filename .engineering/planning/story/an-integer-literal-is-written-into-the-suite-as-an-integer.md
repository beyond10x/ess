## Problem

An authored literal for an `Integer` input is written into the suite as a float. The decoder
that ESS generates for the same field refuses it, so one ESS release's suite and its generated
contract disagree about how an integer is spelled. Reported 2026-10-29 by an adopter on ESS
0.75.0. Checked on the 0.77.0 head (84671d6, `ess 0.77.0`) against the adopter's model at a2a

- `history_length: 1`, typed `Optional<Integer>`, is synthesized as
  `{"history_length":{"kind":"literal","value":1.0}, ...}`. The same happens to `page_size: 1`.
- The generated Rust `integer_at` (`crates/generate/ess-synth/src/rust/json.rs:731`) parses the
  number text as `i64` and refuses `1.0`: "expected an integer, found the number 1.0".
- The interpreted target accepts the literal. The adopter's server, built on the generated
  decoder, refuses it, and the adopter rewrites whole numbers before decoding.

one command, a view over the row, and a `reached_by: network` component. They are served as
`crates/generate/ess-synth/tests/emit_swap_served.rs` serves its model: Rust and Go are built
offline, and the Go cases are skipped where no `go` is on the path, as there.

New file `crates/generate/ess-synth/tests/integer_spellings.rs`:

- `the_rust_server_reads_an_integral_number_with_a_zero_fraction_as_the_integer`: `limit` sent as
  `3.0`, `3e0`, `30e-1` and `-0.0` (as 0) is accepted, and the view row reads back `3` (or `0`).
  `page: 1.0` is accepted too.
- `the_rust_server_still_refuses_a_fraction_an_out_of_range_integer_and_a_hostile_exponent`:

## Fit review

1. Need: an implementation built on the decoders ESS generates can be run against the suite ESS
   synthesizes for the same model, with no rewriting of numbers in between. Reproduced on 0.77.0
   with a minimal `demo.board` model, `limit: Integer` and `page: Optional<Integer>` (a repro
   outside the repository). The authored step `{limit: 3, page: 1}` is written as `"value": 3.0`
   and `"value": 1.0`. The synthesized `demo.board.Open/outcome/opened` writes its `limit` witness
   as `1.0`, so this is not specific to authored scenarios. The generated Rust `integer_at` reads
   the number text as `i64` and refuses `1.0` (`crates/generate/ess-synth/src/rust/json.rs:723-740`).
   The generated Go `integerAt` refuses it through `json.Number.Int64()`
   (`crates/generate/ess-synth/src/go/http.rs:2302-2316`). The adopter's proposal is the story's
   draft acceptance: the suite writes `1`.
2. Class: defect, at the boundary between two ESS outputs. The published contract for `Integer` is
   JSON Schema 2020-12 `type: integer` (`crates/generate/ess-gen/src/types.rs:649-652`,
   `schema.rs:66`), and that dialect counts any number with a zero fractional part as an integer.
   The generated decoders are stricter than the contract they implement. ESS's own served tests
   carry the adopter's workaround: a `json_of` that rewrites `1.0` as `1`
   (`crates/generate/ess-synth/tests/declared_behaviour.rs:1731-1747`). Six other served tests
   in `crates/generate/ess-synth/tests/` define a `json_of` with a `Node::Number` arm; only
   `related_guard_served/mod.rs:430` was read to the same rewrite, the rest are inferred. `crates/verify/ess-conformance/src/witness.rs:119-124` documents the suite's
   `1.0` and leaves the normalising to the runner.
3. Already expressible: no. An adopter can only rewrite numbers in its adapter, which is the
   workaround reported.
4. Fit: two places could change.
   - **The suite's spelling.** `Number`'s `Serialize` writes the binary64 for every value binary64
     carries, by design (`crates/specify/ess-primitives/src/facts.rs:173-210`). The spelling is
     frozen by `docs/design/review-conformance-coverage.md:172` ("integral-float spelling; do not
     coerce to integer or string"). `docs/design/review-primitive-semantics.md:302-321` makes
     changing `1.0` to `1` the "canonical-serialization stage": a format change that needs
     `ess-conformance/6`, an ADR and the relying-reader inventory, because AEP's evidence adapter
     reads the report.
   - **The decoders.** They accept every integral number in `i64` range, however it is spelt, as
     the published schema already does. That changes no suite, contract or wire byte.
5. Second adopter: any Rust or Go service built on `ess generate synthesize` output and held to
   `ess verify conform synthesize` by an adapter that forwards inputs with `serde_json::to_value`
   or `json.Marshal`.
6. Cost of writing `1` in the suite: the bytes of every suite with an `Integer` literal change. In
   this repository that is 56 literals across `suites/generated/{billing,gatepass,oracle-fixture}/suite.json`
   and four committed fixtures (`crates/edge/ess-cli/tests/fixtures/coverage-producers/legacy-observations/billing-{combined,generated}-suite4.json`,
   `crates/verify/ess-diff/tests/fixtures/review-billing-suite-v{4,34}.json`), plus every
   adopter's suite and digest. That breaks a documented contract and a pinned reader (D135).
   Cost of the decoder change: the bytes of the emitted `json` module and Go `wire.go` change. The
   committed trees `generated/rust/gatepass`, `generated/web/billing` and `generated/go/gatepass`
   are regenerated. Generated signatures do not change, and decoding only widens toward the
   published schema.
7. Considered:
   - Change nothing. Rejected: two outputs of one release disagree.
   - Write `1` in the suite. Not this batch: D135 and the design page, as in point 4. It is the
     integer half of story:primitive-canonical-serialization, which already owns it.
   - Add a public helper in `ess-conformance` that renders a `Node` as wire JSON with integers.
     Rejected as the fix: an adapter has to opt in, so the generated decoder still refuses the
     suite as written.
   - Chosen: the generated decoders accept an integral number written with a zero fraction or an
     exponent.

## Decisions

Accept, redesigned (D135: the proposed form breaks a documented contract and has a non-breaking
form).

- **In this batch:** the generated Rust `json::integer_at` and the generated Go `integerAt` read a
  JSON number as an `Integer` when its exact decimal value is an integer in `[i64::MIN, i64::MAX]`,
  whatever the spelling: `3`, `3.0`, `3.00`, `3e0`, `30e-1`, `-0.0`. They still refuse a number
  with a non-zero fraction (`1.5`), one outside `i64` (`9223372036854775808.0`), and a hostile
  exponent (`1e999999999`), quickly and without building the digits. The refusal reads as today:
  "expected an integer, found the number …". The decision is made on the decimal text, never
  through `f64`. Query-string and map-key integers (`keyInteger`, view query parameters) keep their
  text grammar and still refuse `1.0`.
- **The suite keeps `1.0`.** The suite bytes, the report bytes and `Number`'s `Serialize` do not
  change in this batch. The first draft acceptance bullet ("written into the suite as an integer")
  leaves this story for story:primitive-canonical-serialization (active). That story owns
  `ess-conformance/6`, the ADR and the relying-reader inventory
  (`docs/design/review-primitive-semantics.md:302-321`). This story is related to it as
  `informed_by`. No new follow-up story: it would duplicate that one.
- **What the adopter gets:** their adapter can forward the suite's input as written, and the
  generated decoder accepts it. The 0.78.0 changelog says that integral numbers written with a
  fraction are now read as integers by generated Rust and Go servers, as the published schema
  already admits.

No source format, no ADR and no operator choice inside this batch.

## Scope

**Primary surface:** the integer readers emitted by `ess-synth`. Size M: an exact decimal
integral check in two emitted languages, a served end-to-end test, and three regenerated committed
trees.

- `crates/generate/ess-synth/src/rust/json.rs`, `integer_at` (723-740), inside the `JSON` constant.
  Keep the `parse::<i64>()` fast path. On failure, read the grammar the emitted reader already
  validated (`number`, 364-410) as digits plus a decimal exponent, and accept only a
  zero fraction within `i64`. Update the doc comment, which today says an exponent is refused.
  The callers do not change: `rust/wire.rs:965` and `web/bridge.rs:753` (the occurrence index).
- `crates/generate/ess-synth/src/go/http.rs`, `integerAt` (2302-2316), in the emitted Go
  runtime: the same rule on `json.Number`'s text, without `big.Rat` and without `float64`.
  `keyInteger` and the query parameter path do not change.
- The committed trees: `generated/rust/gatepass/crates/gatepass-server/src/json.rs`,
  `generated/web/billing/crates/billing-web/src/json.rs` and `generated/go/gatepass/server/wire.go`.
- New test `crates/generate/ess-synth/tests/integer_spellings.rs`. A `CHANGELOG.md` line.
- Not touched: `crates/specify/ess-primitives/src/facts.rs` (`Serialize for Number`),
  `crates/verify/ess-conformance` and every committed suite. Those belong to
  story:primitive-canonical-serialization.

**Collisions with the other batch-3 units:** none by file. U11, U13 and U14 change suite
synthesis in `ess-conformance`, and this story changes emitted decoders in `ess-synth`. If a
synthesis unit regenerates `suites/generated/*`, it does not meet these files. Within U15 it shares
no file with the repeated-key story.
