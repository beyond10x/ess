## Problem

`story:feature-request-394` realizes a model integer at a native width when an invariant states both bounds, and keeps bundle input (imported JSON Schema or OpenAPI) unchanged. So an imported `{type: integer, format: int64}` generates `serde_json::Number` with a runtime `integer` obligation where the protocol's own SDK has `i64`. Adopter report R10, ess 0.68.0 (15 fields in one catalog).

## Fit review

Re-checked on 2026-10-29 against 0.76.0. Batch 1's #686 changed `crates/generate/schema-contract/src/realize.rs` and moved every line the scoper cited; the citations below are the 0.76.0 lines. The scoper's claims still hold; only the line numbers moved.

1. **Need.** An imported schema's integer that names `format: int32` or `int64` cannot be realized at that width. Minimal reproduction (a repro outside the repository: one component `Counter` with required `wide {type: integer, format: int64}`, `narrow {format: int32}` and `bounded {minimum: 0, maximum: 100}`), re-run on the 0.76.0 release binary with `ess generate schema import-bundle --dialect draft-2020-12` then `types-bundle --target rust` and `--target go`: all three fields are `::serde_json::Number` in Rust and `EssNumber` in Go, `Cargo.toml` turns on the default `exact-numbers` feature, and `types-report.json` reports `…/wide/format` and `…/narrow/format` as "retained in the source bundle; no decoder behavior inferred". The requester's proposal: a native width, plus publishing `minimum` and `maximum`.
2. **Class:** gap. Bundle input cannot state a width at all. Bound-derived widths are model-only (`realize.rs:1569-1572`, `Some(width) if self.model`), and the reproduction's `bounded` (0..100) is still a `Number`.
3. **Already expressible?** For model input, yes, through invariant bounds (#394). For bundle input, no: the schema is the adopter's published contract, and bounds do not help.
4. **Fit with what exists.**
   - This opens the row "bundle integer named format → width" for both bundle formats (`ess-schema-bundle/1` and `/2`).
   - Rust `i32`/`i64` (`realize/rust.rs:674-675`) and Go `int32`/`int64` (`realize/go.rs:394-395`) already exist for `Shape::SizedInteger` (`realize.rs:487`).
   - TypeScript stays `number`, with the precision obligation except for `i32` (`realize/ts.rs:61-72`).
   - Model input is untouched: the generators emit no integer format (grep of non-test code), and the option below does not exist on the model command.
   - The row stays shut for other formats (`uint64`, `int8`), which OpenAPI's data-type table does not define, and for bound-derived bundle widths, which nobody requested.
   - `ess-openapi` keeps `format` on integers as a gap (`crates/generate/ess-openapi/tests/adversary_pass1.rs:126-131`). Carrying it would change stored-envelope replay (`/2`), and that IR feeds no realizer.
   - Generator options that change generated bytes only when asked for already exist under the same report format: `--rust-fold-null` and `--rust-drop-unknown-members` (`RustOptions`, `realize.rs:73-94`; `CHANGELOG.md:146-147`), each held by a test that the default output keeps its digest (`crates/generate/schema-contract/tests/rust_generator_options.rs:76-107`).
5. **A second adopter:** a ledger API whose amounts are `{type: integer, format: int64}` minor units, generated into Go services.
6. **Cost.**
   - Made unconditional, this is breaking for generated bundle libraries whose integers carry `int32`/`int64`: `Number` becomes `i64`, `EssNumber` becomes `int64`, and a crate with no other exact numbers loses its `exact-numbers` feature (inferred from `crates/generate/schema-contract/tests/types_manifest_features.rs:154`). #394 shipped its model width change as breaking (`CHANGELOG.md:1994-1998`), but D135 requires a non-breaking form in this batch.
   - The non-breaking form: one opt-in generator option. No `ess/N`; `ess-schema-bundle/1` and `/2` unchanged; `ess-types-report/3` gains one field that is omitted while the option is off, as `RustOptions` added fields under `/3`.
7. **Alternatives.**
   - Change nothing.
   - Format width by default (the scoper's design). Breaking for every generated bundle library with a format-named integer; out of this batch under D135.
   - Bound-derived width for bundles: misses the need, since these schemas have no bounds.
   - An opt-in option that applies the format width: no consumer changes unless it asks. Chosen.
   - Publishing the range in the projected schema, as requested: dropped, see `## Decisions`.

## Decisions

Decision: **accept, redesigned** (2026-10-29, batch 2 of the open-issue wave). Bound by D135 (`approval-record:d135-a-breaking-unit-leaves-the-batch`): the width is an opt-in, and without it every generated byte stays as 0.76.0 writes it. No `format: ess/N`.

- **Opt-in.** `ess generate schema types-bundle` takes `--integer-format-widths`, for every target. The library takes it as `Plan::from_bundle_with(bundle, roots, &BundleOptions { integer_format_widths: true })`; `Plan::from_bundle` is `from_bundle_with` with `BundleOptions::default()`. `ess generate types` (model input) does not take it. Changed from the request, which asked for the width unconditionally; the default stays the exact-number type because the change breaks generated bundle libraries (D135).
- **Width, with the option.** With bundle input (`!self.model`) an integer node whose `format` is `int32` or `int64` becomes `Shape::SizedInteger` at that width. The format decides the width even beside bounds, and the bounds stay runtime obligations. A `type: [integer, null]` gives `Option<i64>` / `EssNullable[int64]`. Any other format, or no format, keeps `Shape::Integer`.
- **Report, with the option.** The report gains `options: {integer_format_widths: true}`, omitted while the option is off. On the nodes it changes, `format` is reported as "the decoder asserts this format's range (accepted with the integer-format-widths option); `validate-bundle` treats `format` as an annotation" instead of "no decoder behavior inferred". The `integer` and `rust_exact_numbers` obligations at those pointers go away; a crate whose numbers are all format-width integers gets no `exact-numbers` feature.
- **Without the option.** Nothing changes: declarations, `types-report.json`, `Cargo.toml` and `go.mod` keep their bytes.
- **Dropped from the request: publishing the range.**
  - `project-bundle` publishes the source verbatim, and the selected dialect treats `format` as an annotation (`crates/generate/schema-contract/src/bundle.rs:23`, validation with `should_validate_formats(false)` at `:453`).
  - So "a plain validator refuses an out-of-range value" is dropped. The generated decoders refuse; the validator does not; the report records the difference.
- **Already true from #394:** a fractional or `1.0` value is refused by `i64` decoding (inferred for `1.0`; `1.5` is tested below).

## Acceptance

- New file `crates/generate/schema-contract/tests/bundle_integer_formats.rs`; run each with `cargo test -p schema-contract --locked --test bundle_integer_formats <fn>`:
  - `the_default_output_keeps_its_bytes`: for the reproduction's bundle, `from_bundle` and `from_bundle_with(BundleOptions::default())` realize Rust, Go and TypeScript to the digests frozen from 0.76.0 before the change (declarations, report with the generator version masked, `Cargo.toml`/`go.mod`), as `rust_generator_options.rs::defaults_are_unchanged` does.
  - `an_imported_int64_realizes_as_i64`: with the option, Rust `i64` and Go `int64`; `int32` gives `i32`/`int32`.
  - `an_imported_integer_without_format_keeps_the_exact_number_type`: with the option, `Number`/`EssNumber`, with the `integer` obligation.
  - `an_unknown_integer_format_keeps_the_exact_number_type`: `uint64` and `int8`.
  - `a_format_width_holds_beside_bounds`
  - `a_nullable_int64_realizes_as_an_optional_i64`
  - `the_decoder_refuses_a_value_outside_the_format_range`: compiles the Rust crate and Go module (compile helper as in `rust_realization.rs:307` and `go_realization.rs:236`). Refuses 2^31 for `i32`, 2^63 for `i64`, and 1.5.
  - `the_report_records_the_option_and_names_the_asserted_format`: the `options` field appears only with the option; includes TypeScript `int32` dropping its precision obligation.
  - `a_bundle_whose_integers_all_name_a_width_gets_no_exact_numbers_feature`: with the option; without it, the feature stays.
  - `validate_bundle_still_treats_format_as_an_annotation`
- `model_input_widths_are_unchanged`: the existing tests stay green, byte for byte: `cargo test -p schema-contract --locked --test integer_widths`.
- The existing default-digest tests stay green unchanged: `cargo test -p schema-contract --locked --test rust_generator_options`.
- CLI: `the_integer_format_widths_option_reaches_every_target`: `cargo test -p ess-cli --locked --test schema_bundle the_integer_format_widths_option_reaches_every_target` (with the flag Rust gets `i64`; without it the files equal 0.76.0's).
