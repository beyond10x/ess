## Need

Reported by an adopter's server implementation (tracker rows 33 and 34, 2026-10-22, ESS 0.67.0;
still present in 0.69.0). A generated Rust server reads back the answer it wrote itself with the
same JSON reader that guards intake, and that reader stops at one depth constant. A command with a
`Json`-typed field (for example `metadata: Optional<Json>`) can legitimately carry a value nested
deeper than the read-back allows, so:

- `entry::read` panics on the `.expect("this crate's encoders write JSON its reader reads")`, and
- `handle`, which ends `Ok(entry::read(&body))`, turns a valid request into a 500 or a panic.

The adopter works around it with its own reader at depth 128 and by avoiding `handle`.

## Where it lives

- `crates/generate/ess-synth/src/rust/json.rs:42-48`: one `DEPTH = 64` for every read; its comment
  says no model this emitter produces nests that deep, which is false for `Json` fields.
- `crates/generate/ess-synth/src/rust/http.rs:2128-2134` (`entry::read`, the `.expect`) and `:1057`
  (`handle`).
- The generated Go target uses its own reader with no depth constant (grep); not affected as far as
  is known.

## Acceptance

- A request whose `Json` field nests to the deepest level intake admits is answered by the
  generated `dispatch` and `handle` with its declared outcome: no 500, no panic. Test in
  `ess-synth` builds a generated crate and drives both entry points with that request.
- A request nested one level deeper than intake admits is still refused 400 at intake, with the
  same body as today; a test asserts it.
- Reading back the server's own answer never panics: the read-back either has no depth limit or a
  limit that intake cannot exceed, and the `.expect` is gone or provably unreachable (a test drives
  the deepest admitted value through `handle`).
- Generated bytes change only in the reader and `entry::read`; the generated-crate pins in
  `ess-synth` move for that reason alone, and each moved pin is named.
