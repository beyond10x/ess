## Need

Generated Rust and Go behaviour must answer a view with no source, and a view field reading a fixed
setting, from the specification, as the interpreter does; until this story `ess-synth` refuses
such a view by name (`story:a-view-may-answer-values-no-row-holds`). Entity Runtime lowering must
refuse it by name, never drop it.

## Acceptance

- The Rust and Go code `ess generate` writes for the reproduction answers the `Limits` view with
  one row `{max_tags: 20, api_level: 1}` on an empty store, and a sourced view's `setting.` field
  with the fixed value; the generated packages' own tests assert both
  (`cargo test -p ess-synth --locked --test generated_view_queries`).
- The synthesized suite of `story:conformance-reads-a-view-no-row-holds` passes against the
  generated Rust and Go targets.
- Entity Runtime lowering refuses a sourceless view and a `setting.` field by name: two new rows
  of `CONSTRUCTS` (`crates/generate/ess-entity-runtime/src/subset.rs`), shown on the page
  `website/docs/reference/entity-runtime-lowering.md` rendered from it.
- Specifications without such views keep their generated bytes: the `ess-synth` byte-pin targets
  `served_codec_names` and `go` pass with no row re-pinned.

## Fit review

1. **Need.** Generated targets answer what the interpreter answers.
2. **Class: gap** (follows from the construct).
3. **Already expressible?** No.
4. **Fit.** Every target handles a construct or refuses it by name (assessing skill, question 4);
   a fixed value is a constant in generated code, no settings struct needed for the first cut.
5. **Second adopter.** Any adopter generating a Rust or Go service with a limits endpoint.
6. **Cost.** Generated code changes only for specifications using the construct.
7. **Alternatives.** (a) Keep generated targets refusing: the construct works on the interpreter
   only. (b) Chosen.
