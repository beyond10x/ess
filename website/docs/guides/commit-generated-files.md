# Commit what a reviewer reads, regenerate the rest

Adding ESS to an existing repository writes more files than the change you made. Commit the files
a reviewer or a consumer reads. Rebuild the rest in CI, where they cannot drift unseen.

| artifact | commit? | regenerated by | drift check |
|---|---|---|---|
| specification sources (`system.yaml`, domains, components, topology) | yes | nobody: you write them | `ess specify validate` |
| `ess-inputs.yaml`, with its `requires: ess X.Y.Z` pin | yes | nobody: you write it | an older `ess` refuses it; `--strict-requires` refuses a newer one |
| authored scenarios, listed in `ess-inputs.yaml` | yes | nobody: you write them | `ess specify validate` compiles them against the model |
| `ess-known-failures/1` declarations | yes | nobody: you write them | `ess verify conform run --known-failing` refuses a stale one |
| compiled IR | no | `ess specify compile`; compiling twice is byte-identical | none needed |
| run reports, histories and mutation output | no | rerunning the suite, the explorer or `ess verify conform mutate` | none needed |
| projections a consumer reads, selected with `--kind`: `openapi`, `asyncapi` or `schema`, with `.ess-output` | yes | `ess generate --kind <kind> --out <root>` | the same command with `--check` |
| `site` and `docs` projections | no; build them in CI for publication | `ess generate --kind site` or `--kind docs` | none needed |
| synthesized runner and suite (`--target go` or `--target typescript`) | yes | `ess verify conform synthesize` | regenerate, then fail CI on a dirty tree |
| synthesized code your implementation links | yes | `ess generate synthesize` | regenerate, then fail CI on a dirty tree |
| planning store and evidence | see [AEP](https://beyond10x.github.io/docs/aep/concepts/planning-store/) | AEP | AEP |

Commit `.ess-output` with the projections it records. It is what lets a clone, a second worktree or
CI regenerate the same files in place; see
[repeated generation and recovery](./generate-artifacts.md#repeated-generation-and-recovery).
[Commit the generated runner](../concepts/test-pyramid.md#commit-the-generated-runner) explains why
the synthesized runner is committed rather than imported. The pin is described in
[name the `ess` release](./specify/layout-and-validation.md#name-the-ess-release-the-specification-is-maintained-with).
[Drift-checking in CI](./generate-artifacts.md#drift-checking-in-ci) shows the `--check` run.

## Why the first diff is large

Without `--kind`, `ess generate` writes all five projections. For `examples/billing` that is 48 files,
plus the `.ess-output` record: 29 under `schema/`, 9 under `site/`, 6 under `docs/`, and 2 each under
`openapi/` and `asyncapi/`. `site/assets/mermaid.min.js` alone is about 3.5 MB.

Select what a consumer reads with `--kind`, one owner per command, and leave the rest to CI:

```shell-session
$ ess generate --path spec --kind openapi --out generated
$ ess generate --path spec --kind openapi --out generated --check
```

A regeneration that changes nothing writes nothing, so a committed tree stays clean until the
specification changes.
